# MVP 存储、DAO 访问与数据保留

[English](2026-11-17-mvp-storage-dao.en.md) | 中文

## 范围与状态

本 Note 汇总截至 2026-11-17 的存储讨论和官方资料调研，沿用[框架 Note](2026-11-17-mvp-framework.zh.md)、[节点执行 Note](2026-11-17-mvp-node-execution.zh.md)及[插件 Note](2026-11-17-mvp-plugins.zh.md)。DAO 在这里泛指业务数据访问能力，范围包括关系数据库、文档／KV 存储、文件／对象存储、搜索／向量引擎及外部数据服务等。

按照 [MVP 维护约定](../../AGENTS.md)，合入主分支前保持 proposed，可随讨论和实现自由编辑。本文分别记录已明确的方向、本轮本地实现和未定细节。三档需求匹配、SQLite 工具提供者、命名空间及 TTL 明细已有可运行实现，具体范围见下文。原型接口、图和 SQLite Schema 继续没有历史兼容承诺，本轮也不引入数据库 Schema 编写标准。

## 已明确的设计方向

插件命名空间确定表的归属。表内资源还需遵循账户边界，三档 DAO 的调用都应从可信上下文取得账户范围。共享物理库的读写、查询、索引和数据关联同样按账户隔离。首版所有者访问及双账户验收见[账户服务与权限 Note](2026-11-19-mvp-account-identity.zh.md)。

- 所有 DAO 类型的访问统一按三档表达：跨底层实现的一致封装、针对具体底层的封装、直接使用原生访问入口。
- DAO 采用松散的工具包方式提供可复用逻辑。插件在调用时传入目标表等访问对象，负责业务表的创建、结构和使用；访问能力绑定与具体操作目标分别处理。
- 插件声明实际需求，提供者声明实际提供的契约和能力，框架据此检查可满足性并形成绑定或缺失说明。
- 插件可以在自己的逻辑命名空间内按需建表，框架不额外设置表数上限；数据归属与具体后端实现分别记录。
- 常见数据形态可以通过模板托管；中间明细的保留期限与长期数据的保留需要显式表达。
- 模板及清理实现可以由内置存储插件提供。基础设施与插件的具体划分仍待细化，最小框架读取自身目录和诊断的能力必须独立于可选实现。

## 按封装程度划分的 DAO 三档访问

| 档位 | 对使用方提供什么 | 需求与可移植边界 |
| - | - | - |
| 跨底层实现一致封装 | 不同底层实现遵守相同的操作和行为契约，例如记录、内容读写、搜索或 TTL 数据集。 | 使用方依赖公共契约；只匹配实际实现了该契约的提供者。统一语义的具体范围由每个契约定义。 |
| 针对具体底层的封装 | 为某种底层实现提供专项接口，保留特有类型、查询能力和行为，例如 FTS5 或 PostGIS 专项服务。 | 使用方声明相应专项服务及必要条件；不同底层的专项接口可以不同。 |
| 原生访问 | 直接取得数据库连接、SDK 客户端、文件句柄或访问会话，使用原生操作。 | 使用方声明所需后端、扩展和实例条件，自行负责具体操作。框架承担约定的绑定与访问生命周期。 |

第二档提供面向相应底层的专项接口。数据库类型、数据形态、封装档位分别表达；原生访问覆盖各类 DAO 的原生入口。

三档是按每项访问需求选择的方式，一个插件可以混用。提供者按实际能力发布相应档位，无须为了凑齐分类实现所有封装。三档不代表信任等级或权限沙箱；完全信任及框架元数据独占写入的约定继续有效。

框架共同处理提供者发现、配置、访问实例、需求匹配、绑定生命周期和诊断。事务、排序、分页、TTL、搜索语义等按具体契约声明，不假定所有 DAO 都具有数据库语义。工作流端口和跨设备执行通信仍由执行层维护；DAO 服务可由业务直接调用，也可通过节点参与可选工作流。

公共基础契约应与 SQLite 原生类型分离，专项封装和原生入口可以暴露各自后端需要的类型。将 SqliteConnection 替换为 DbConnection 只能减少驱动类型依赖，SQL、DDL、索引和事务差异仍需具体实现处理。成熟驱动或 ORM 可作为实现手段，当前未选定统一 ORM，也未设计自有通用查询语言。

## DAO 工具包与调用目标

框架提供可复用的 DAO 操作逻辑，插件使用时传入目标表。插件负责创建表、维护结构和索引，并选择访问哪张表；DAO 工具依据选定契约执行操作。第一档统一的是操作和行为语义，具体表仍由插件在调用时指定。

同一套 TTL 明细工具由 RSS 传入自己的抓取明细表，也可由另一业务传入自己的明细表，复用过期处理逻辑。本轮使用 DaoTable(namespace, name) 描述目标，IRecordDao 提供建表、Put、Read、Keep 和 DeleteExpired；记录模板使用 key、JSON value 及可空 expires_at，业务自己调用建表辅助。任意业务列映射及通用查询尚未实现，复杂 RSS 表继续通过原生关系连接访问。

这种调用方式延伸到所有 DAO：文档访问传入集合，搜索传入索引，对象／文件访问传入相应位置或对象目标。三档封装方式继续有效，不强迫这些目标具有同一种表结构。

参与提供者匹配的是所需 DAO 工具、连接能力与访问实例。具体表作为操作参数传入，调用工具本身不要求框架预先逐表登记、推断 Schema 或接管业务表生命周期。需要统一后台保留或跨插件数据协作时，另外显式提供相应目标、策略及必要描述。

## 声明、检查与执行计划

本轮 DaoRequirement 声明插件内的需求名称、Mode、Contract、Instance 及可选 Backend；DaoCapability 发布实际提供的档位、契约、实例和后端。默认实例名为 workspace，当前仅装配共享 SQLite 工作区。匹配使用这些字段，缺失或存在多个候选时给出原因，调用方通过 DaoScope.Get 取得相应服务。

声明在 Configure 阶段独立保存。装配器先让可激活的提供者发布能力，再绑定依赖它的插件，避免清单顺序决定成败。SQLite 提供者实际尝试创建临时 FTS5 表，只在成功时发布搜索能力。本轮粒度为插件级必需需求：RSS 需要原生连接和记录工具，文章需要原生连接和 FTS5，各项需求只影响声明它的插件；核心与诊断仍可运行。多实例配置、节点级可选能力及更丰富的探测结果仍待细化。

例如，一个 RSS 插件可以为抓取明细申请统一 TTL 契约，为检索申请 FTS5 专项封装，并为其他操作申请某种原生连接。声明“全文搜索”是否足够，取决于使用方需要的分词、排序和查询行为是否已经包含在明确的契约中；框架不根据名称推断语义相等。

提供者／连接能力的匹配与具体表的存在、结构适配分别处理。框架检查显式声明的前提；运行时才确定的访问目标，其实际访问结果在使用处解释。具体表作为调用参数，并不自动成为插件启动依赖。

插件级必要服务依赖、某个 DAO 访问需求，以及某张图中的跨业务连线分别维护。本轮装配检查 DAO 需求，工作流继续通过已激活节点生成计划；缺失实现保留原图和归属说明。按具体节点、每次运行或远程实例重新绑定 DAO 资源尚未实现，后续应保持创建时可行性与执行时实际条件的区别。

匹配成功表示检查时声明的前提成立。实际连接中断、SQL 错误、外部提交结果未知等由运行期如实报告，重试及业务副作用仍遵循既有协议和节点契约。历史需求与归属以普通 JSON 描述保留，读取不依赖缺失插件的 CLR 对象构造。SQLite 目前实际探测 FTS5 是否可用；更丰富的提供者健康状态及失败详情仍待细化。

## 命名空间与所有权

以稳定的插件身份划分逻辑命名空间，插件在其中按需求定义表、字段、索引、约束及查询。框架维护命名空间归属及必要名称映射，私有业务表访问不以逐表登记为前提。索引、视图等对象同样需要避免命名冲突；数据库表之外的文件位置、对象键或服务资源，按实际后端表达对应绑定。

本轮 DaoNames 将命名空间和本地名分别作 UTF-8 十六进制编码，以固定前缀及分隔符组成表／索引名称。它保留正常 Unicode 名称与大小写差异，避免下划线拼接歧义，并使动态 SQL 标识符仅含固定前缀和十六进制字符；记录值与搜索语句仍使用参数。该映射用于当前 SQLite 实现，其他后端需按自身约束适配。SQLite 的 schema 名称对应 main、temp 或附加数据库，不能直接套用独立命名空间的假设。[SQLite 名称解析](https://www.sqlite.org/lang_naming.html)

数据拥有者、DAO 提供者及模板／清理能力提供者可能不同。RSS 的明细数据仍归 RSS 所有，使用通用托管模板不会把业务所有权转交给存储插件。

框架独占其元数据写入；业务和存储插件通过约定接口提交声明、业务结果及生命周期变更意图，由框架登记。原生访问仍须遵守所有权契约。当前同进程、完全信任的条件下，依靠可信代码契约维护归属；数据库权限隔离及 SQL 拦截不属于当前方案。

## 持久化、保留期限与数据引用

是否落盘、保留多久和存放在哪里分别约定。最近一段时间的中间明细可以持久化；长期业务结果可以同样位于 SQLite，也可能在其他存储中。

| 数据角色 | 存储责任与保留方向 |
| - | - |
| 框架元数据 | 框架管理插件／数据归属、关系、工作流及必要目录，缺失实现时仍可读取。 |
| 业务数据 | 业务插件维护字段、约束、查询及业务保留要求，避免把复杂业务全部压成统一 KV 文档。 |
| 内容与快照 | 文件、附件、原始抓取等可使用独立内容存储；身份、归属与可用位置需要关联。 |
| 运行状态与记录 | 执行计划、结果、输入快照、排队消息、同步组和节点状态具有不同的持久化要求。 |
| 可回收数据 | 由明确的保留策略授权回收；不能仅因被称作“中间数据”或“缓存”就推断可丢弃。 |

逻辑业务对象、某次不可变内容快照、内容所在位置和运行时载荷引用分别建模。文章 ID 可以在内容更新后保持不变；重放需要引用当次输入快照及必要上下文。文章插件会更新同一文章的标题和正文，仅保留其 ID 不足以重现历史输入。同步输入的 messagekey 也不自动成为上述身份。

进程内继续通过只读对象引用高效传递，不因引入持久存储而强制每条消息先落盘。有限重放需要保留输入、配置、节点实现信息及影响状态的同步输入和消费顺序。活动队列、未齐同步组与节点状态的恢复仍按框架／节点 Note 继续讨论，TTL 不自动解决这些问题。

## 模板工具与保留机制

模板以工具包形式提供建表、读写和适用的生命周期操作，插件选择模板并在调用时传入目标表。首轮普通持久记录与 TTL 明细共用 IRecordDao：空过期时刻表示长期保留，显式时刻表示可到期的记录。Read 按 key 排序返回记录，当前没有通用筛选、分页或自定义列／索引接口；业务仍可通过专项封装或原生访问维护其他结构。

本轮新增 storage.sqlite 内置核心插件，统一提供记录模板、FTS5 专项封装、原生 IConnectionSource 及清理任务。它在发行清单中不可关闭，文件缺失仍允许最小框架启动。最小 SQLite 元数据基础设施留在框架，独立保存插件与清理委托目录；公共 DAO 契约不依赖 SQLite 驱动类型。清理是普通插件后台任务，服务启动后先执行一轮，再按 cleanupInterval 周期执行，默认一分钟；这只是清理调度周期，不是数据保留期限。CLI 模式不自动启动后台任务。

TTL 工具可以由业务插件主动调用；统一后台清理需要通过 PluginRegistration.Retentions 明确委托所需记录 DAO 和目标表。每行的 expiresAt 决定期限。委托以拥有者／目标为键持久化，重复装配保留已保存的启停意图；dao pause/resume 控制后续清理轮次，已开始的操作可以完成。本轮采用暂停／恢复保留委托，删除委托及跨实例调度仍未实现。调用辅助工具或采用模板本身不自动登记清理。

框架只能依据明确的保留契约执行相应生命周期操作。复杂业务表、外部内容、特殊索引或多表关系的清理责任由对应实现声明；登记归属或采用某个访问档位本身不授予通用删除权限。框架不会仅凭表名猜测 TTL 列或业务依赖。

### TTL 的候选语义

中间明细显式声明过期时刻，空时刻表示长期保留。RSS 抓取明细的 detailRetention 默认未设置，因此不会自动过期；配置正时长后，以抓取完成时刻计算新记录期限，配置变化不改写旧记录。没有统一的数据大小、表数或保留时长上限。

记录工具保存毫秒精度的绝对 expiresAt，Put 显式写入或替换记录及期限，读取不续期。Read 默认隐藏 expiresAt 小于等于传入 now 的记录，诊断读取可显式包含它们。DeleteExpired 仅删除目标表中已经到期的记录；Keep 将仍存在记录的期限置空，已到期但尚未删除的记录也可保留，已删除则返回未找到。当前每目标执行一条删除语句，没有承诺精确删除时刻；大规模回收的批次和时间预算留待实际负载细化。Flink 对刷新、可见性和清理方式的分离仍作为参考。[Flink State TTL](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/fault-tolerance/state/#state-time-to-live-ttl)

本轮 TTL 的应用范围是完成抓取后的观察明细，仅记录 URI、字节数和完成时间，既不保存原始正文，也不充当重放输入或检查点。记录没有登记为框架数据对象，清理不删除业务对象或关系。长期保留已支持 Keep；活动执行的保留引用、依赖传播与崩溃后释放尚未实现，不能把该工具直接当作可靠队列或节点状态后端。后续涉及执行输入时需要先确定持有规则，不能静默丢弃待处理消息或半个同步组。

过期后是否保留精简的状态或来源记录、如何处理关系及特殊索引，需要独立约定；不能假定删除主体后其引用自然有效。SQLite 删除通常留下可复用页面，数据库文件收缩属于另一项维护操作。[SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)

### 与插件启停保留约定的关系

禁用或缺失本身不构成清理条件；没有明确保留策略的数据继续遵守插件 Note 的保留边界。常规 TTL 是预先声明的数据生命周期，独立于显式 cleanup／uninstall hook，不能借自动保留任务调用这些维护 hook。

本轮采用：数据拥有者禁用或缺失而记录／清理提供者仍可用时，继续执行已持久委托的清理；提供者缺失时标为 unavailable，保留数据、委托和既有期限，最小框架可继续查看目录。提供者恢复后沿用期限处理，插件重新装配不覆盖暂停设置。Read 的到期可见性按所用工具契约处理；提供者缺失时相关 DAO 不可用，不把记录自动续期或假装成功读取。

插件自己调用 TTL 工具的任务仍随插件不可用而暂停，未委托目标不会自动进入统一清理。清理目录持久记录上次尝试时间、删除数量和错误；一个目标失败不阻断其他目标。本轮不验证插件对业务清理 hook 的语义遵守情况，也不调用这些维护 hook。数据持有和跨实例恢复继续待定。

## 事务、后端选择与公网设备

本轮继续以同一个 SQLite 工作区保存框架、RSS 和文章表。BusinessStorage 接受显式 IConnectionSource，仅对框架工作区的同一源提供业务写入与元数据登记原子性；其他源需要另行协调，不会被误当作同一事务。文章的 FTS 索引更新同样参与文章写入事务。SQLite WAL 下通过 ATTACH 访问多个数据库，不提供整组数据库的崩溃原子性。[SQLite WAL](https://www.sqlite.org/wal.html)

支持多 DAO 提供者和按数据集／功能绑定实例是设计方向，不等于所有数据能透明换库或共享一个事务。数据库与文件、外部索引或其他服务分别提交时，需要确定权威状态、元数据登记顺序、失败与未知结果的处理。当前同库原子性不能直接推广到这些组合。

数据拥有者负责相应 Schema 和实现变化，MVP 不因此新增通用迁移平台或历史兼容要求。ADO.NET 公共类型减少类型耦合，ORM 可以辅助实现；即使使用 EF Core，多提供程序的迁移也仍需分别维护。[ADO.NET](https://learn.microsoft.com/sql/connect/ado-net/introduction-microsoft-data-sqlclient-namespace)、[EF Core 多提供程序迁移](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/providers)

未来设备通过公网协作，数据身份、可用位置与传输路径需要分离。当前倾向各实例管理本地存储，执行计划绑定 DAO 资源并安排必要传输；SQLite WAL 不能作为跨设备共享数据库文件的协作机制。通用资源描述、实例选择、连接恢复、凭据管理和存储迁移留待资源模型与实际操作细化。

备份恢复应按完整工作区考虑：数据库、需要持久保存的内容、配置和必要密钥。多存储的一致备份、文件与目录提交、导入导出及数据搬迁仍未设计；原生或专项 DAO 的恢复要求需要由相应实现提供。

## 当前实现与下一轮验证

[DAO 契约与工具入口](../../src/LazyTuiHub.Dao/) 不引用 SQLite 驱动；[SQLite 提供者插件](../../plugins/LazyTuiHub.Plugin.TuiHub.Storage.Sqlite/) 实现统一记录工具、FTS5 专项服务及原生连接源。[SqliteDatabase](../../src/LazyTuiHub.Framework/SqliteDatabase.cs) 仍作为最小工作区基础设施；[BusinessStorage](../../src/LazyTuiHub.Framework/BusinessStorage.cs) 使用 DbConnection／DbTransaction 协调工作区原子登记。[PluginRegistration](../../src/LazyTuiHub.PluginSdk/PluginRegistration.cs) 通过 Daos、DaoServices 和 Retentions 收集声明，框架保存普通描述以支持提供者缺失诊断。

[RssStore](../../plugins/LazyTuiHub.Plugin.TuiHub.Rss/runtime/RssStore.cs) 保存订阅，[RssDetails](../../plugins/LazyTuiHub.Plugin.TuiHub.Rss/runtime/RssDetails.cs) 使用通用记录工具保存抓取明细。[ArticleStore](../../plugins/LazyTuiHub.Plugin.TuiHub.Articles/runtime/ArticleStore.cs) 在 articles 命名空间管理文章及全文索引，通过同一事务提交内容、索引及可选的来源关联。关闭 RSS 后仍可阅读和搜索文章。新版表结构和默认图使用新的工作区。

产品测试覆盖工具对多个目标的复用、命名空间与标识符安全、到期可见性、长期保留、暂停状态跨启动保留、拥有者关闭时继续受托清理、模式／实例／后端匹配、首次缺失能力、提供者 DLL 移走／恢复，以及搜索、业务与框架登记共同回滚。既有本地／HTTP、图和插件保留场景继续通过。当前只有一个实际后端，跨后端兼容性、其他专项能力、内容快照及持久运行状态仍需真实用例验证。

## 尚需讨论的决策与顺序

| 优先级 | 决策 | 需要确定的内容及原因 |
| - | - | - |
| 下一轮细化 | 需求绑定扩展 | 当前为插件级必需声明和单工作区实例；节点级可选能力、多实例配置、远程资源重新绑定及更丰富的诊断需按实际用例细化。 |
| 随查询需求 | DAO 工具扩展 | 当前为 JSON 记录模板与 FTS5 专项接口；其他字段映射、查询／分页和索引辅助由实际需求推动。原生连接由调用方释放，语义可移植范围通过其他提供者验证。 |
| 执行输入持久化前 | TTL 与执行保留 | 当前观察明细可直接按期限回收；执行输入的持有、释放、崩溃恢复、普通关联与强保留引用仍需单独确定。后台委托永久撤销及大规模清理预算也待细化。 |
| 首个外部存储用例 | 跨事务域登记 | 当前仅承诺同一工作区源的原子登记；多库、文件或外部服务需要明确权威状态、登记顺序及未知结果的恢复方式。 |
| 随首个内容用例 | 对象、快照与位置标识 | 引用的作用域、可变实体与不可变内容的关系、关联是否保留内容、过期后的描述，以及跨实例解析。决定跨业务复用与有限重放的依据。 |
| 随部署与运维需要 | 物理布局及完整恢复 | 单库／分库、内容目录、Schema 初始化、备份快照一致性、迁移与导入导出。遵循 MVP 无历史兼容承诺，不提前建立通用迁移体系。 |
| 随运行恢复与多设备需要 | 持久现场及资源策略 | 排队消息、未齐同步组、节点状态的持久性；并发、连接复用、资源预算、保留引用释放、远程可用性与数据搬迁。不会从某个默认 TTL 或有界队列推导整体恢复和内存保证。 |

本轮通过 RSS 与文章插件涉及的三档访问需求及一次明细写入／到期流程落实了最小方案。后续继续按具体用例收敛上述边界，以明确、可替换的简单行为推进，不要求所有存储问题先获得最终答案。
