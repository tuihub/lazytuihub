# MVP 固定主节点与任务协调

[English](2026-11-19-mvp-coordination.en.md) | 中文

## 职责与现状

唯一的固定主节点构建并推进全部执行计划，调度所有任务。主节点离线时，系统不可用。它安装的插件决定整个部署支持的业务，并提供工作流、节点契约与实现。本机资源和权限满足时，主节点可独立执行完整业务。主节点运行独立的账户服务，保存设备登记、账户资源绑定、工作流、计划和执行尝试。账户服务独占凭据记录。[账户与权限](2026-11-19-mvp-account-identity.zh.md)

MVP 以主节点的已安装插件清单为基准，强制校验每个参与任务执行的从节点。插件 ID 集合及对应版本须完全一致。缺少插件、多装插件或版本不同，主节点应指出差异，将该从节点排除在派发候选之外。这项校验只针对参与执行的服务端设备，独立连接远程服务的 client 仍按用户身份访问。各设备分别上报可用资源和可执行操作。

当前原型已从本机注册表取得节点实现并校验工作流。协调端查询对端清单并主动调用工作节点，账户模式下按设备任务授权筛选可重复操作的候选，按业务 URI 校验属主绑定写入，并传递请求的账户范围。存储绑定采用配置中唯一的 `workspace.primary` 资源。现有协议只上报资源和导出的操作，跨设备插件清单校验和从节点轮询仍待实现。 [框架 Note](2026-11-17-mvp-framework.zh.md) · [当前工作流校验](../../src/LazyTuiHub.Plugins/Workflows/WorkflowRuntime.cs) · [当前工作节点协议](../../src/LazyTuiHub.Api/Protos/lazytuihub/execution/v1/worker_service.proto)

## 从资源需求到执行计划

| 输入 | 提供者 | 计划器据此判断 |
| - | - | - |
| 逻辑图、端口和资源需求 | 定义工作流的插件及参与节点的契约 | 每一步需要访问哪些输入、输出和能力 |
| 有效 URI 权限 | 主节点账户服务 | 运行主体及其本次凭据是否允许这些访问 |
| 资源绑定、设备清单和可用性 | 主节点与各设备 | 已绑定资源由谁承载，哪些设备开放所需能力 |

用户通过 client 凭用户会话发起业务操作。插件定义该操作所需的工作流，协调器在本次调用的授权上下文中派发步骤。设备代用户发起操作时，接收端验证设备身份和用户对该设备的委托。主节点把运行主体、目标账户和适用的委托记录到运行中，按节点契约核对步骤实际访问的 URI。新建、重试或回退的执行尝试都受本次运行的有效权限约束。工作流定义可以描述资源需求，由计划选择设备和传输路径。[主节点授权模型](2026-11-19-mvp-account-identity.zh.md)

计划器依据资源绑定找到数据服务。比如，运行主体对目标文章库 URI 有写权限，计划器就按该资源的权威绑定找到承载它且开放相应存储服务的设备。数据承载位置属于放置信息，权限仍以文章库 URI 判定。设备上报 SQLite 能力只提供候选信息，改变权威绑定须由主节点更新。

步骤使用某台设备提供的网络或计算能力时，该能力属于实际访问的资源。计划器筛选候选设备时检查候选所对应的能力 URI，和用户直接使用该能力时采用同一条授权。主节点在本机执行每个具备条件的步骤。若资源登记或权威绑定已表明本机无法执行，主节点可直接将该步骤委派给具备条件的从节点。若执行时才发现本机不可达等可用性故障，仅在操作允许重试时降级。每次委派均须满足原有权限和资源绑定，从节点只执行领到的步骤。已绑定资源的承载设备离线时，计划保留原绑定并解释无法执行的原因。

## 轮询、执行与恢复

1. 已登记的从节点以设备身份通过 HTTPS 向固定主节点报告资源并轮询领取任务。空闲时主节点可以挂起请求，有任务时立即返回。设备登记阶段对领取码的轮询由账户服务处理，此处的任务轮询只对已获身份的设备开放。常规控制操作沿用仓库的 Proto 与 HTTP 契约。[API 开发指南](../../docs/development/api-design.zh.md)
2. 主节点先持久化本次尝试的账户、运行、步骤、目标设备、操作和资源，再以该尝试标识定向派发。交付前复核目标设备身份、本次尝试使用的 URI 权限及资源绑定，再以原子状态变更记录派发并返回任务。只有设备的回执能证实对端已收到任务。并发轮询不能重复产生同一次派发。处于等待中的连接，在返回任务前同样必须通过这次复核。
3. 设备核对目标、操作、任务中的账户范围及本机导出约束，使用本地实现执行，再凭设备身份和尝试标识回报进度、结果或失败。主节点只接受匹配设备对该尝试的合法状态推进。重复回执返回已记录的结果，旧尝试的迟到消息不能覆盖后续尝试。计划和诊断区分“尚未派发”“已派发、等待设备回报”“已完成”“已失败”和“结果未知”。
4. 轮询或网络连接中断只改变可达性。重连时先按既有尝试核对状态。可重复操作遇到可用性故障时，主节点可以创建新尝试并改选符合条件的设备。所有者写入一旦可能交付，就保留原尝试，等所有者用执行记录或业务事务结果核实。无法核实时报告结果未知，禁止自动重发写入。主节点重启后按持久化的派发记录恢复判断。保存派发状态不等于持久化全部流数据或重放整张图。

撤销设备身份、设备使用权或用户的数据权限后停止受影响的领取与回退，向已交付的工作请求协作取消。对端失联时，主节点仍保留可能已经发生的外部写入。已撤销的凭据不能提交回执；需要核实的写入由获准的主体从所有者执行记录或业务数据中对账。权限失败、网络故障和业务拒绝分别进入诊断。

## 流式任务与代理

首版通过轮询领取任务和普通 HTTPS 请求提交结果。轮询的交付单位是一次计划分配的工作，其标识独立于 HTTP 请求。未来，主节点可以在已领取的流式任务中给出获准连接的端点和会话标识，从节点再主动发起持久连接，例如 WebSocket。接收端验证设备身份，以及该会话对应的账户、尝试、端点和流向。持续数据、反压及取消可沿该连接传递。重连仍对应原尝试。流的续传位置、缓冲与传输协议在实现流式任务时确定。

从节点身份、任务目标、连接路径分别记录。首版主从直连。将来 C 可通过 B 中继与主节点建立端到端认证和加密连接，B 只转发流量。计划和回执的目标仍是 C。B 如也执行工作，须用自己的设备身份领取自己名下的任务。中继断线不转移任务或数据所有权。

轮询参考 GitLab Runner，需求与资源的独立声明参考 HTCondor，保留端点身份的中继参考 Syncthing。固定主节点仍是规划和授权决策者。[GitLab 长轮询](https://docs.gitlab.com/ci/runners/long_polling/) · [HTCondor ClassAds](https://htcondor.readthedocs.io/en/latest/classads/classad-mechanism.html) · [Syncthing 中继](https://docs.syncthing.net/users/relaying.html)

## 协调机制的验收场景

- 在 M 上刷新 Bob 的订阅。本机具备所需资源和权限时，即使有可用的空闲从节点，抓取、解析和入库也全部在 M 完成。
- 在 M、B、C 安装相同插件，改用仅 B 可达的 RSS 源，并将 Bob 的文章库绑定到 C。Bob 执行同一个刷新操作。验证 M 生成并推进整个计划。源在 M 上不可达时，由 M 将抓取委派给 B。M 在本机解析，按文章库的绑定将写入派给 C。文章及来源关联写入 C，所需权限仍取决于文章库 URI，Bob 可以没有 C 的通用任务使用权。
- 分别让从节点缺少一个插件、多装一个插件或使用不同版本，验证主节点指出具体差异并停止向该设备派发；恢复一致后，可按其可用资源重新参与执行。
- 在缺少 B 使用权时，计划和回退均排除 B。若交付前撤销该授权，正在等待的轮询也收不到任务。诊断能区分权限不足、所需资源缺失以及承载设备离线。
- 模拟 C 已提交写入而回执丢失，随后重启 M 并让 C 重连。主节点用原尝试接收补报，不再发起写入。缺少结果证据时继续显示结果未知。持久数据连接和中继的运行验收留给相应实现。
