# MVP 可信插件边界与无损启停

[English](2026-11-17-mvp-plugins.en.md) | 中文

## 范围与状态

本 Note 记录业务插件化的边界及 2026-11-17 的官方文档／源码调研结论，为可插拔原型提供方向，不定义完整插件系统。沿用[框架 Note](2026-11-17-mvp-framework.zh.md)与[节点执行 Note](2026-11-17-mvp-node-execution.zh.md)；业务服务可直接调用，节点是参与可选工作流的适配入口。

[存储与 DAO Note](2026-11-17-mvp-storage-dao.zh.md) 记录后续 DAO 三档访问、命名空间、托管模板与保留策略的讨论，并区分已明确方向和待定语义。

当前已有可运行的冷启动原型，具体范围见下文。按照 [MVP 维护约定](../../AGENTS.md)，本 Note 合入主分支前保持 proposed，允许随代码迭代自由编辑。实现提交同时更新本 Note，区分已实现行为、简单临时选择和未定边界，不为探索性旧接口、图或 Schema 建立兼容层。

## 固定边界与职责

| 边界 | 约定 |
| - | - |
| 运行方式 | 宿主与插件始终在同一进程，通过直接 C# 调用协作。 |
| 加载方式 | 动态加载 .NET 托管程序集 DLL；一个逻辑插件可包含入口程序集、附属依赖和资源。 |
| 生命周期 | 仅冷启动加载；启停配置和程序集替换在下一次启动生效，不承诺运行中装卸。 |
| 信任 | 插件完全受信任，共享进程权限和资源；本轮不建立沙箱或权限隔离系统。 |
| 核心插件 | 发行清单将核心插件标记为 required；当前 core 提供问候功能及内置定时器／HTTP 节点，不可手动关闭。 |
| 最小框架 | 加载器、框架元数据存储及必要诊断独立于插件实现，在插件缺失时仍能启动。 |

宿主负责启动配置、发现与装配、共享服务容器和应用生命周期。业务插件拥有业务服务、业务存储及初始化、节点适配、HTTP 适配器、CLI 与 GUI 共享的类型化操作和后台任务。通用框架库和共享契约不因采用 DLL 就全部成为可选插件。既有 Proto／HTTP 约定继续有效，本轮不另行设计插件管理 API。

## 源码归属与插件协作

每个插件 ID 对应 [plugins](../../plugins/) 下的一个源码根目录和根目录中的一个 C# 项目。后端、共用前端逻辑、GUI、CLI、公开类型和资源随同一 DLL 交付。小插件可以平铺文件；业务增多时按职责分目录。包和源码目录建议使用 ID 的 PascalCase 写法。迁出到独立仓库时可调整项目引用、构建配置、脚本和 CI，业务源码保持原样。

插件根项目声明 PluginId、显示名 Title、可选的 PluginVersion 和各 PluginEntryPoint 的角色与类型。基础 SDK 的构建规则生成插件清单并嵌入 DLL。发行索引从所选项目取得 ID 和 DLL 文件名，由宿主指定核心成员。入口共享插件身份和启停状态。编译器核对入口类型和接口，冷启动时宿主先读程序集元数据，再实例化当前模式所需的入口。入口可使用 internal，提供公开无参构造函数。

| 运行方式 | 宿主调用已声明的入口 |
| - | - |
| 仅服务端 | Server |
| 本地 GUI 或 CLI | Server 和 Client，再加上与界面对应的 ClientGui 或 ClientCli |
| 连接远端的 GUI 或 CLI | Client，再加上与界面对应的 ClientGui 或 ClientCli |

Server 注册业务服务、节点和后台任务。Client 注册两种界面共用的操作，按连接方式绑定本地服务或 HTTP 适配器。ClientGui 和 ClientCli 各自注册界面交互。无界面宿主可以使用同一 DLL，前提是服务端和共用客户端的类型及初始化可在该宿主解析。宿主提供所需依赖时，每个操作系统只需分发一个插件 DLL。私有依赖和外部资源随 DLL 交付。

插件项目引用 [LazyTuiHub.Sdk](../../src/LazyTuiHub.Sdk/)，取得入口契约、构建声明和工作流执行接口。包名、程序集名和根命名空间一致。工作流、DAO 和交互类型保留各自的命名空间，通过包依赖提供。插件通过 NodeRegistration 注册节点，通过 IWorkflowExecutor 请求执行工作流。宿主管理节点注册表、计划执行和插件目录。提供 Proto 端点的插件还可引用共享的 API 传输工具。

基础 SDK 的 `StreamWorkflow.Chain` 按声明顺序连接标准流端口，生成普通节点和边，保留节点归属、设置和资源要求。手工连线与顺序连线共用框架的规划器和执行器。API 构建工具生成插件自有的传输适配。业务插件定义 provider 操作及其预期结果。

ClientGui 入口可再引用 [LazyTuiHub.Sdk.Avalonia](../../src/LazyTuiHub.Sdk.Avalonia/)，用 `AddDesktopPage<TPage>` 按类型注册控件或提供页面工厂，响应工作区更新，并使用共享的页面模型、自适应布局与动效。桌面宿主提供当前主题，通过 RunDesktopOperation 跟踪界面操作，负责窗口、主题切换和关闭流程。将渲染类型放在 GUI 代码中，同一 DLL 的服务端和 CLI 入口即可在无界面宿主加载。

插件优先通过工作流节点提供可复用能力，允许其他插件直接引用其有意公开的 public 类型。直接引用由双方维护语义与兼容性，框架仅核对显式声明的插件依赖。插件自己决定如何组织公开类型。例如，[游戏插件的 provider 类型](../../plugins/LazyTuiHub.Plugin.TuiHub.Games/Providers/)供 Steam、Bangumi 和 VNDB 直接引用。文章插件公开文章草稿和订阅来源接口，RSS 实现该接口，阅读器按服务可用性显示订阅功能。

## 插件标识与资源命名空间

每个插件在项目文件中声明稳定 ID，格式为 `lazytuihub.plugin.<发布者>.<插件名>`。发布者占一段，插件名可用点分段。每段使用小写 ASCII 字母和数字，词间可用连字符。宿主精确匹配完整 ID。插件依赖、工作流节点归属、插件 ACL 命名空间和存储归属都引用这个 ID。版本单独声明。宿主在同一进程中对每个 ID 至多装配一个插件实例。同一插件可部署到多台设备，各处沿用同一 ID。设备 ID 另行标识部署位置。

项目名、入口程序集名和插件自有 C# 类型的根命名空间默认采用包含发布者的完整插件 ID 的点分 PascalCase 写法。例如，游戏插件的入口程序集为 LazyTuiHub.Plugin.TuiHub.Games.dll，公开类型为 LazyTuiHub.Plugin.TuiHub.Games.GameEntry。其他发布者可以在自己的前缀下使用相同的业务类型名。.NET SDK 默认将项目名用于 AssemblyName 和 RootNamespace。另行命名项目时，可显式设置这两个属性。插件的 HTTP 客户端与手写 partial 类位于插件命名空间下，Proto 决定生成的传输类型的命名空间。PackageId 独立指定 NuGet 包名，只改包名即可沿用原有 CLR 类型名和消费方的 using。调整公开命名空间属于 C# API 变更。

安装目录使用完整的小写 PluginId。修改该 ID 后重新构建，发行索引、项目间依赖、资源 URI 及新工作流均使用新身份。既有工作区按原身份保存。平台标识、CLI 命令和节点类型沿用业务名称。

业务插件贡献受权限控制的资源时，以自己的插件 ID 作为 URI 的首个命名成分。框架按加载时确认的插件 ID 绑定注册的命名空间，插件定义命名空间内的资源标识及读写语义。账户归属与资源标识仍由该资源的声明确定。[账户身份与权限 Note](2026-11-19-mvp-account-identity.zh.md)

## 插件关系与版本

每次冷启动都按当前进程选用的插件检查关系。本地宿主使用已选中、已启用且 DLL 存在的插件。远程前端检查自己的发行目录。A 在项目中声明关系，构建从目标项目读取 PluginId，宿主从 DLL 读回声明。

| A 对 B 的声明 | B 缺席或停用 | B 的版本匹配 | B 的版本超出范围或未声明所需版本 |
| - | - | - | - |
| requires（依赖） | 阻止 A | 先调用 B 的入口，本地激活 A 还需要 B 已激活 | 阻止 A，报告 B、要求的范围和实际版本 |
| compatibleWith（兼容） | A 可独立启动 | A 可在使用联动功能时接入 B，双方没有顺序要求 | 同样阻止 A，B 继续按自己的声明启动 |

在 ProjectReference 或 PackageReference 上声明 PluginRelation 和可选的 PluginVersionRange。前者从被引用项目读取 ID，后者从 NuGet 包携带的构建元数据读取 ID。PluginProjectReference 只读取另一项目的身份，PluginReference 直接引用已知 ID。PluginAlias 将引用的 ID 提供给业务代码，工作流可据此标明节点归属。只声明别名不会约束插件的加载顺序。省略版本范围表示接受任意版本。插件可用 SemVer 表达主、次、修订和预发布版本。宿主用 NuGet.Versioning 匹配已安装的版本：`1.2.0` 表示至少 1.2.0，`[1.2.0]` 为精确版本，`[1.0.0,2.0.0)` 包含下界、排除上界；`1.*` 使用 NuGet 的浮动匹配。每个 ID 仍只装配一个已选实例。Steam、Bangumi、VNDB 都依赖游戏插件的 `[1.0.0,2.0.0)` 接口。[NuGet 版本与范围](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning) · [SemVer](https://semver.org/)

宿主在调用入口前根据本次选用的插件清单校验版本。A 和 B 可互相声明 compatibleWith，各自的范围只约束声明方。只有 requires 决定入口调用顺序及依赖环诊断，本地激活还会等待硬依赖和所需 DAO 就绪。若版本匹配的 B 配置或激活失败，A 仍可独立运行其余功能。插件在入口中注册服务或工厂，在使用可选功能时解析对方的能力；启动过程中看到的激活状态可能随后变化。工作流连线由执行计划处理。

Factorio 的可选依赖也会在目标存在且版本不符时阻止声明方，另有单独的互斥声明。本轮采用依赖和兼容。三个游戏 provider 可以共存，命令重名已有注册诊断。若出现两个实现独占同一进程资源，或只需排除某个已知有问题的版本，再以实际冲突决定是否增加互斥关系及其处理方式。[Factorio 模组依赖](https://lua-api.factorio.com/latest/auxiliary/mod-structure.html#dependencies)

## 框架元数据所有权

框架独占自身元数据的写入与生命周期。插件贡献能力声明、业务结果和必要的关联意图，由框架在注册或业务提交边界登记；插件不得直接修改核心元数据表，也不获得任意增删改元数据的管理接口。这条边界同时服务直接业务调用和节点执行，不要求所有写入都经过工作流。

框架持久保存识别缺失能力所需的信息，包括插件身份与来源、节点／数据类型归属、必要的端口与类型声明、工作流原始参数和连线，以及已有数据身份、关联、任务定义和配置。原型将它们与业务表放在同一 SQLite 中。BusinessStorage 负责事务提交：插件写业务表并返回包含数据身份、关联意图的 BusinessChange，框架登记元数据后一起提交，失败同时回滚。DataCatalog 公开关联查询，修改方法收归框架私有。共享数据库仍依靠可信所有权契约，插件只能写自己的业务表。

这些描述必须能在没有插件代码时读取，不依赖插件 CLR 对象的构造或自定义反序列化。当前运行时的严格类型匹配在实现可用时进行；缺失实现不能阻止读取描述。跨插件调用仍须共享同一程序集类型身份，不能仅凭类型名称相同就认定可连接。

声明目录独立于插件部署目录。扫描 DLL 只能发现当前存在的实现，不能代替框架保存的历史声明。新导入的工作流应携带必要来源信息；如果既无历史记录也无来源声明，只能报告未知节点类型，不按名称前缀猜测所属插件。缺失节点保留参数与连线，不自动剔除或修补图。

完全信任、同进程运行下，禁止插件操作框架元数据是代码契约和所有权边界，通过接口与存储分层落实，不宣称它构成进程内安全隔离。

## 启用意图、可用性与本次激活

分别记录用户保存的启用选择、当前文件／依赖的可用性，以及本次启动的绑定和激活结果。界面可以统一呈现不可用，但原因需要保留。用户启用了 RSS 而 DLL 缺失时，不把配置改成禁用；实现恢复后仍按原有选择重新绑定。

“关闭”同时包括主动禁用，以及框架启动时未找到插件。缺失、禁用和无法加载都保留声明与诊断，基础框架继续启动；相关业务入口隐藏或不可用，相关任务不启动、不再调度，管理与诊断仍能识别其归属。核心插件的不可关闭是正常配置约束，缺失时也采用这套可用性语义，依赖它的能力保持不可用。

启动按职责分阶段：读取框架目录和启用意图，发现并加载可用实现，汇总服务与能力贡献，建立共享服务容器和节点注册，再绑定实现、生成需要运行的计划并启动任务。注册顺序不能碰巧决定跨插件工作流是否可用。声明元数据由框架更新，不让插件任意改全局注册状态。

后端采用 IApplicationPlugin 入口，通过 PluginRegistration 贡献服务、节点、数据类型、默认工作流、命令、路由、任务和可选 hook。PluginRuntime 在宿主构造前暂存服务贡献，在激活前暂存节点和端点声明。清单中的硬依赖决定入口调用顺序，硬依赖和 DAO 需求共同决定本地激活条件。全部节点注册完成后才保存默认工作流并检查任务可执行性。不承诺插件副作用及后续激活失败的全局回滚。

原型使用默认 AssemblyLoadContext 和统一依赖基线，保留共享契约的严格类型身份。AssemblyDependencyResolver 定位附加托管依赖，尚不支持独立依赖版本及任意原生依赖部署。[.NET 官方插件教程](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support)为 DLL／依赖处理提供参考，不要求本项目采用私有加载上下文。本轮没有运行中卸载、私有版本求解、市场或热更新。

## 无损启停与清理 hook

框架承诺反复启停不引入数据损失。在插件没有专门清理行为时，变化仅限于其功能不可见／不可用和任务停止运行。启停或缺失不触发业务数据、框架元数据、配置、工作流、任务定义及关联的删除、重置或覆盖，重新启用不重复创建默认任务或用默认值覆盖用户修改。

这项保留必须在插件完全不在场时成立，不能依赖插件执行关闭 hook。框架负责元数据和关联，保留对暂不可解析对象的引用，不扫描或理解插件业务数据以执行清理。业务清理属于对应插件；框架不因缺失、禁用或引用不可解析而补做清理。

明确的托管保留契约授权常规过期，数据拥有者与清理提供者可能不同。这种授权独立于插件启停及显式维护 hook；没有声明策略的数据继续按上述边界保留。记录工具隐藏到期行，Keep 可清除到期时间。持久目标委托在拥有者关闭／缺失而提供者仍激活时继续清理；提供者缺失时保留数据及策略并报告不可用，暂停意图在重新装配后保留。RSS 观察记录默认长期保留，配置的过期不作用于文章或执行输入。存储 Note 记录这些已实现语义，以及持久输入与恢复的待定决策。

| 操作 | 行为边界 |
| - | - |
| 关闭／启动时缺失 | 按可用性停止相关能力和任务，保留数据与定义，不调用数据清理或卸载 hook。 |
| 再次开启／实现恢复 | 使用原有身份、配置和数据重新绑定，恢复功能及调度资格。 |
| 显式清理数据 | 框架可提供统一入口，调用插件可选的清理 hook；范围和业务行为由插件实现。 |
| 显式卸载 | 框架可提供统一流程及可选卸载 hook，与禁用、数据清理分开；具体代码移除流程待定。 |

hook 只依靠契约约束。框架处理调用、进度、返回结果、异常和取消，但不扫描数据库／文件来证明清理完整，也不验证实现是否符合 hook 的业务定义。插件缺失时如实报告相应 hook 不可用，不假装调用成功或自行补偿。hook 不获得框架元数据所有权。

运行期资源释放与持久数据清理分别约定。停止任务、释放连接等可沿用 Host／DI 的协作取消和释放机制，不把停止等同于数据清理，也不由框架验证插件的释放实现是否忠实遵守契约。

无损目标不能被静默缩小为“只要保存图即可”。当前活动流队列、未齐同步输入和节点局部状态仅在内存中；停机后如何保留未完成数据及恢复进度仍需确定。现有取消机制不能被称为无损暂停，重新执行也不自动证明没有损失。插件重新可用后的恢复、错过定时任务的处理与副作用语义留待后续决策，不在本 Note 假定补跑或从原指令续跑。

| DeepSeek Harness／Cordis | [服务依赖与注册释放](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)连接插件；[插件管理](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/plugin-manager/README.md)区分选择、文件可用性与运行结果，缺失时保留描述。 | 共享契约连接提供者与使用者，独立保存启用意图，运行期注册与资源有明确归属。 |
| Jellyfin | [.NET 插件管理](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Plugins/PluginManager.cs)加载程序集、注册 DI 服务并记录故障状态；[官方说明](https://jellyfin.org/docs/general/server/plugins/)将配置保留与插件文件重装分开。 | 用 .NET 原有装配和生命周期机制实现原型，代码、声明和业务数据分开管理。 |

Factorio 明确说明[原型移除会使存储引用失效](https://lua-api.factorio.com/latest/auxiliary/migrations.html)，不能照搬这种行为实现我们的启停无损。它在声明阶段允许 mod 修改其他原型，也不等同于本项目禁止插件操作框架元数据的边界。DeepSeek Harness 的可替换服务、配置分层和热更新范围更广，本轮只借鉴组合与状态分离，不复制整套系统。

最值得保留的是：声明长期可读、当前实现可缺失；用户意图不被加载失败改写；再次绑定不重置持久状态；运行期收尾与显式业务清理分开。不可关闭核心插件、框架元数据独占写入及 hook 仅靠契约约束，仍以本项目明确约定为准。

## 当前原型与验证

后续[桌面实现](2026-11-17-mvp-ui-comparison.zh.md) 将普通页面身份／标题声明纳入框架拥有的插件元数据。Avalonia 工厂位于桌面层，桌面阅读器依赖文章库，RSS 插件激活时提供订阅操作。导航使用本次已激活插件入口的页面。目录按入口保存已观察到的页面和命令，在切换宿主模式、停用或缺失时仍可读取。桌面与 Web 宿主共用服务装配，桌面激活接收服务提供者，不映射 HTTP 端点；既有任务和冷启动保留语义对两种宿主均生效。

宿主选择发行插件并标记核心项。构建与发布将已内嵌清单的程序集及所需私有文件放入各自的 `plugins/<id>/` 目录。发行索引 plugins/plugins.json 记录插件 ID、DLL 文件名和核心标记。替换已选插件后，下一次冷启动会读取新清单中的版本与关系。元数据目录独立于部署目录，保留启停意图、设置及能力声明。

核心、RSS、文章和 SQLite 插件 使用同一入口契约。公开 DAO 契约位于 LazyTuiHub.Dao，插件声明访问需求，与具体表目标分开；提供者发布能力，使用者匹配档位／契约／实例／底层后激活，不依赖清单顺序。首次启动无法激活的使用者也保留需求／提供声明。存储插件提供记录／TTL、FTS5、原生连接及委托清理；缺失时最小框架元数据仍可用。RSS 拥有自己的 API 实现、协议适配、CLI 命令、初始化和刷新任务。最小宿主保留插件管理、DAO 诊断／保留控制及工作流查看、编辑、执行入口。WorkflowRuntime 负责图存储、注册与计划，业务服务获得 IWorkflowExecutor。既有 RSS 业务操作仍通过工作流，让它们不再强制依赖工作流留待后续迭代。

--command plugins 提供 list/inspect、enable/disable、不透明配置及显式 cleanup/uninstall hook 调用。修改保存后要求重启，不改变本次激活状态。禁用插件作为维护目标时可在冷启动加载服务／hook，但不激活节点、路由、命令和任务。hook 暂时返回 Task，命令报告完成、异常和取消，不验证清理语义，也没有专用进度协议。RSS 尚未提供这两种 hook。uninstall 仅调用可选 hook，不删除代码或目录记录。

--command workflow 在插件缺失时仍可使用。保存时保留不可用节点、参数、连线和 pluginId 来源，同时返回当前可执行性诊断；执行必须能生成有效计划。无来源的未知导入类型保持未知。默认工作流仅在不存在时插入，不覆盖用户修改。持久任务声明保留归属和所需工作流名称，运行状态暂不持久化。正常服务启动只运行可用且所需工作流能够生成计划的任务，每个插件任务一份；宿主停止时协作取消，重试由业务任务决定。

产品测试通过独立 CLI 进程和同一工作区，验证 RSS 启用／禁用／缺失／恢复、文章与已读状态／关联／配置／不透明图参数保留、核心和清单缺失诊断、未知导入类型及任务／命令不可用。生命周期测试覆盖冷启动维护、仅显式调用 hook 且不验证清理语义、任务取消，以及业务与元数据事务同时回滚。存储测试补充覆盖提供者 DLL 缺失／恢复、首次启动的需求不可用、三档访问、仅委托目标清理、长期记录、暂停持久化及 FTS／业务／目录共同回滚。既有本地／生成 HTTP 场景继续通过动态插件运行。

初始化失败收尾、统一基线之外的依赖部署、持久运行现场、丰富的 hook 结果／进度及真正的代码移除仍需细化。本轮建立可运行的装配边界，不构建完整插件平台，也不宣称已经支持无损暂停运行现场。
