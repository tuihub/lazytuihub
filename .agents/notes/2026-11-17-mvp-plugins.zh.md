# MVP 可信插件边界与无损启停

[English](2026-11-17-mvp-plugins.en.md) | 中文

## 范围与状态

本 Note 记录业务插件化的边界及 2026-11-17 的官方文档／源码调研结论，为可插拔原型提供方向，不定义完整插件系统。沿用[框架 Note](2026-11-17-mvp-framework.zh.md)与[节点执行 Note](2026-11-17-mvp-node-execution.zh.md)；业务服务可直接调用，节点是参与可选工作流的适配入口。

[存储与 DAO Note](2026-11-17-mvp-storage-dao.zh.md) 记录后续 DAO 三档访问、命名空间、托管模板与保留策略的讨论，并区分已明确方向和待定语义。

当前已有可运行的冷启动原型，具体范围见下文。按照 [MVP 维护约定](../../AGENTS.md)，本 Note 合入主分支前保持 proposed，允许随代码迭代自由编辑。实现提交同时更新本 Note，区分已实现行为、简单临时选择和未定边界，不为探索性旧接口、图或 Schema 建立兼容层。

## 固定边界与职责

| 边界 | 约定 |
| - | - |
| 运行方式 | 宿主与插件始终在同一进程，通过直接 C# 调用协作。 |
| 加载方式 | 动态加载 .NET 托管程序集 DLL；一个逻辑插件可包含入口程序集、附属依赖和资源。 |
| 生命周期 | 仅冷启动加载；启停配置和程序集替换在下一次启动生效，不承诺运行中装卸。 |
| 信任 | 插件完全受信任，共享进程权限和资源；本轮不建立沙箱或权限隔离系统。 |
| 核心插件 | 发行清单将核心插件标记为 required；当前 core 提供问候功能及内置定时器／HTTP 节点，不可手动关闭。 |
| 最小框架 | 加载器、框架元数据存储及必要诊断独立于插件实现，在插件缺失时仍能启动。 |

宿主负责启动配置、发现与装配、共享服务容器和应用生命周期。业务插件拥有业务服务、业务存储及初始化、节点适配、HTTP／CLI 入口和后台任务。通用框架库和共享契约不因采用 DLL 就全部成为可选插件。既有 Proto／HTTP 约定继续有效，本轮不另行设计插件管理 API。

插件的必要服务依赖与工作流的数据连线分别处理。某张图将 RSS 连接到另一业务，不表示 RSS 插件本身必须依赖那个插件。缺少节点实现时说明受影响的工作流；缺少必要服务时说明相应插件或能力无法激活，不阻断独立能力。

## 框架元数据所有权

框架独占自身元数据的写入与生命周期。插件贡献能力声明、业务结果和必要的关联意图，由框架在注册或业务提交边界登记；插件不得直接修改核心元数据表，也不获得任意增删改元数据的管理接口。这条边界同时服务直接业务调用和节点执行，不要求所有写入都经过工作流。

框架持久保存识别缺失能力所需的信息，包括插件身份与来源、节点／数据类型归属、必要的端口与类型声明、工作流原始参数和连线，以及已有数据身份、关联、任务定义和配置。原型将它们与业务表放在同一 SQLite 中。BusinessStorage 负责事务提交：插件写业务表并返回包含数据身份、关联意图的 BusinessChange，框架登记元数据后一起提交，失败同时回滚。DataCatalog 公开关联查询，修改方法收归框架私有。共享数据库仍依靠可信所有权契约，插件只能写自己的业务表。

这些描述必须能在没有插件代码时读取，不依赖插件 CLR 对象的构造或自定义反序列化。当前运行时的严格类型匹配在实现可用时进行；缺失实现不能阻止读取描述。跨插件调用仍须共享同一程序集类型身份，不能仅凭类型名称相同就认定可连接。

声明目录独立于插件部署目录。扫描 DLL 只能发现当前存在的实现，不能代替框架保存的历史声明。新导入的工作流应携带必要来源信息；如果既无历史记录也无来源声明，只能报告未知节点类型，不按名称前缀猜测所属插件。缺失节点保留参数与连线，不自动剔除或修补图。

完全信任、同进程运行下，禁止插件操作框架元数据是代码契约和所有权边界，通过接口与存储分层落实，不宣称它构成进程内安全隔离。

## 启用意图、可用性与本次激活

分别记录用户保存的启用选择、当前文件／依赖的可用性，以及本次启动的绑定和激活结果。界面可以统一呈现不可用，但原因需要保留。用户启用了 RSS 而 DLL 缺失时，不把配置改成禁用；实现恢复后仍按原有选择重新绑定。

“关闭”同时包括主动禁用，以及框架启动时未找到插件。缺失、禁用和无法加载都保留声明与诊断，基础框架继续启动；相关业务入口隐藏或不可用，相关任务不启动、不再调度，管理与诊断仍能识别其归属。核心插件的不可关闭是正常配置约束，缺失时也采用这套可用性语义，依赖它的能力保持不可用。

启动按职责分阶段：读取框架目录和启用意图，发现并加载可用实现，汇总服务与能力贡献，建立共享服务容器和节点注册，再绑定实现、生成需要运行的计划并启动任务。注册顺序不能碰巧决定跨插件工作流是否可用。声明元数据由框架更新，不让插件任意改全局注册状态。

临时采用 IApplicationPlugin 入口，通过 PluginRegistration 贡献服务、节点、数据类型、默认工作流、命令、路由、任务和可选 hook。PluginRuntime 在宿主构造前暂存服务贡献，在激活前暂存节点和端点声明。必要插件 ID 形成简单的启动依赖图，提供方缺失或激活失败会阻止依赖方激活；工作流连线不形成这种服务依赖。全部节点注册完成后才保存默认工作流并检查任务可执行性。不承诺插件副作用及后续激活失败的全局回滚。

原型使用默认 AssemblyLoadContext 和统一依赖基线，保留共享契约的严格类型身份。AssemblyDependencyResolver 定位附加托管依赖，尚不支持独立依赖版本及任意原生依赖部署。[.NET 官方插件教程](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support)为 DLL／依赖处理提供参考，不要求本项目采用私有加载上下文。本轮没有运行中卸载、私有版本求解、市场或热更新。

## 无损启停与清理 hook

框架承诺反复启停不引入数据损失。在插件没有专门清理行为时，变化仅限于其功能不可见／不可用和任务停止运行。启停或缺失不触发业务数据、框架元数据、配置、工作流、任务定义及关联的删除、重置或覆盖，重新启用不重复创建默认任务或用默认值覆盖用户修改。

这项保留必须在插件完全不在场时成立，不能依赖插件执行关闭 hook。框架负责元数据和关联，保留对暂不可解析对象的引用，不扫描或理解插件业务数据以执行清理。业务清理属于对应插件；框架不因缺失、禁用或引用不可解析而补做清理。

明确的托管保留契约授权常规过期，数据拥有者与清理提供者可能不同。这种授权独立于插件启停及显式维护 hook；没有声明策略的数据继续按上述边界保留。记录工具隐藏到期行，Keep 可清除到期时间。持久目标委托在拥有者关闭／缺失而提供者仍激活时继续清理；提供者缺失时保留数据及策略并报告不可用，暂停意图在重新装配后保留。RSS 观察记录默认长期保留，配置的过期不作用于文章或执行输入。存储 Note 记录这些已实现语义，以及持久输入与恢复的待定决策。

| 操作 | 行为边界 |
| - | - |
| 关闭／启动时缺失 | 按可用性停止相关能力和任务，保留数据与定义，不调用数据清理或卸载 hook。 |
| 再次开启／实现恢复 | 使用原有身份、配置和数据重新绑定，恢复功能及调度资格。 |
| 显式清理数据 | 框架可提供统一入口，调用插件可选的清理 hook；范围和业务行为由插件实现。 |
| 显式卸载 | 框架可提供统一流程及可选卸载 hook，与禁用、数据清理分开；具体代码移除流程待定。 |

hook 只依靠契约约束。框架处理调用、进度、返回结果、异常和取消，但不扫描数据库／文件来证明清理完整，也不验证实现是否符合 hook 的业务定义。插件缺失时如实报告相应 hook 不可用，不假装调用成功或自行补偿。hook 不获得框架元数据所有权。

运行期资源释放与持久数据清理分别约定。停止任务、释放连接等可沿用 Host／DI 的协作取消和释放机制，不把停止等同于数据清理，也不由框架验证插件的释放实现是否忠实遵守契约。

无损目标不能被静默缩小为“只要保存图即可”。当前活动流队列、未齐同步输入和节点局部状态仅在内存中；停机后如何保留未完成数据及恢复进度仍需确定。现有取消机制不能被称为无损暂停，重新执行也不自动证明没有损失。插件重新可用后的恢复、错过定时任务的处理与副作用语义留待后续决策，不在本 Note 假定补跑或从原指令续跑。

## 调研结论与采用范围

以下来自调研时的官方资料；“借鉴”是本项目的设计选择，不表示引入对应依赖，也不把参考实现当作本项目无损保证的证明。

| 项目 | 观察到的机制 | 本项目借鉴 |
| - | - | - |
| ComfyUI | [加载器](https://github.com/Comfy-Org/ComfyUI/blob/master/nodes.py#L2255)记录导入失败并继续；[前端](https://github.com/Comfy-Org/ComfyUI_frontend/blob/main/src/scripts/app.ts#L1328)收集缺失节点类型、实例与可用来源信息。 | 描述载入与可执行性分开，保留缺失节点和归属诊断。 |
| Factorio | [生命周期](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)区分声明、初始化、读档和配置变化；运行期原型不再可改。 | 每次启动绑定与业务数据初始化分开，生命周期阶段各司其职。 |
| DeepSeek Harness／Cordis | [服务依赖与注册释放](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)连接插件；[插件管理](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/plugin-manager/README.md)区分选择、文件可用性与运行结果，缺失时保留描述。 | 共享契约连接提供者与使用者，独立保存启用意图，运行期注册与资源有明确归属。 |
| Jellyfin | [.NET 插件管理](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Plugins/PluginManager.cs)加载程序集、注册 DI 服务并记录故障状态；[官方说明](https://jellyfin.org/docs/general/server/plugins/)将配置保留与插件文件重装分开。 | 用 .NET 原有装配和生命周期机制实现原型，代码、声明和业务数据分开管理。 |

Factorio 明确说明[原型移除会使存储引用失效](https://lua-api.factorio.com/latest/auxiliary/migrations.html)，不能照搬这种行为实现我们的启停无损。它在声明阶段允许 mod 修改其他原型，也不等同于本项目禁止插件操作框架元数据的边界。DeepSeek Harness 的可替换服务、配置分层和热更新范围更广，本轮只借鉴组合与状态分离，不复制整套系统。

最值得保留的是：声明长期可读、当前实现可缺失；用户意图不被加载失败改写；再次绑定不重置持久状态；运行期收尾与显式业务清理分开。不可关闭核心插件、框架元数据独占写入及 hook 仅靠契约约束，仍以本项目明确约定为准。

## 当前原型与验证

后续[桌面实现](2026-11-17-mvp-ui-comparison.zh.md) 将普通页面身份／标题声明纳入框架拥有的插件元数据。Avalonia 工厂位于桌面层，rss.desktop 作为独立 DLL 依赖 rss。导航只接入已激活插件，缺失／关闭的页面声明仍可读取。桌面与 Web 宿主共用服务装配，桌面激活接收服务提供者，不映射 HTTP 端点；既有任务和冷启动保留语义对两种宿主均生效。

宿主构建 core、RSS 和 storage.sqlite 发行产物，不在运行时依赖它们的实现程序集。从应用输出目录的 plugins/plugins.json 或 --plugin-directory 读取显式清单；清单声明身份、入口 DLL／类型、核心标记和必要服务依赖。plugin_catalog 独立于部署目录，保留清单观察、启用意图、不透明 JSON 配置及普通声明快照。清单或文件缺失时仍保留历史目录记录；即使程序集身份已缓存，也先检查文件是否存在。

LazyTuiHub.CorePlugin、LazyTuiHub.Rss 和 LazyTuiHub.Storage.Sqlite 使用同一入口契约。公开 DAO 契约位于 LazyTuiHub.Dao，插件声明访问需求，与具体表目标分开；提供者发布能力，使用者匹配档位／契约／实例／底层后激活，不依赖清单顺序。首次启动无法激活的使用者也保留需求／提供声明。存储插件提供记录／TTL、FTS5、原生连接及委托清理；缺失时最小框架元数据仍可用。RSS 拥有自己的 API 实现、协议适配、CLI 命令、初始化和刷新任务。最小宿主保留插件管理、DAO 诊断／保留控制及工作流查看、编辑、执行入口。WorkflowRuntime 负责图存储、注册与计划，业务服务获得 IWorkflowExecutor。既有 RSS 业务操作仍通过工作流，让它们不再强制依赖工作流留待后续迭代。

--command plugins 提供 list/inspect、enable/disable、不透明配置及显式 cleanup/uninstall hook 调用。修改保存后要求重启，不改变本次激活状态。禁用插件作为维护目标时可在冷启动加载服务／hook，但不激活节点、路由、命令和任务。hook 暂时返回 Task，命令报告完成、异常和取消，不验证清理语义，也没有专用进度协议。RSS 尚未提供这两种 hook。uninstall 仅调用可选 hook，不删除代码或目录记录。

--command workflow 在插件缺失时仍可使用。保存时保留不可用节点、参数、连线和 pluginId 来源，同时返回当前可执行性诊断；执行必须能生成有效计划。无来源的未知导入类型保持未知。默认工作流仅在不存在时插入，不覆盖用户修改。持久任务声明保留归属和所需工作流名称，运行状态暂不持久化。正常服务启动只运行可用且所需工作流能够生成计划的任务，每个插件任务一份；宿主停止时协作取消，重试由业务任务决定。

产品测试通过独立 CLI 进程和同一工作区，验证 RSS 启用／禁用／缺失／恢复、文章与已读状态／关联／配置／不透明图参数保留、核心和清单缺失诊断、未知导入类型及任务／命令不可用。生命周期测试覆盖冷启动维护、仅显式调用 hook 且不验证清理语义、任务取消，以及业务与元数据事务同时回滚。存储测试补充覆盖提供者 DLL 缺失／恢复、首次启动的需求不可用、三档访问、仅委托目标清理、长期记录、暂停持久化及 FTS／业务／目录共同回滚。既有本地／生成 HTTP 场景继续通过动态插件运行。

初始化失败收尾、统一基线之外的依赖部署、持久运行现场、丰富的 hook 结果／进度及真正的代码移除仍需细化。本轮建立可运行的装配边界，不构建完整插件平台，也不宣称已经支持无损暂停运行现场。
