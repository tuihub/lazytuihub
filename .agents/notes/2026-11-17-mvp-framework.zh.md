## 选型始终可调整

MVP 合入主分支前，可按最终交付需要替换框架、依赖、协议、存储、Schema 和组件边界。比较依赖库已有能力及其替代方案，用证据界定限制适用于哪个版本或平台。取舍时排除已投入的工作、更换原型的成本和对废弃方案的兼容。冻结的仓库与 API Note 按各自的规则修订。[仓库约定](../../AGENTS.md)

交付后的维护责任、第三方依赖的稳定性和未来切换成本都影响选型。评估时也应考虑自维护组件。

## 目标与应用边界

应用采用 C/S 单体结构，支持进程内低成本调用，以及跨进程、跨设备的常规 HTTP 通信；未来的 WebSocket 保留独立适配边界。沿用[协议基线](2026-11-15-protobuf-api-contract.zh.md)，业务逻辑由 C# 实现，生成覆盖契约和通信代码。工作流内部端口并不因此全部成为公开 API。

RSS 插件管理订阅、抓取明细和 RSS／Atom 解析。解析节点输出共用的 ArticleDraft 流。文章插件接受任意生产者输出的该类型，管理文章身份、存储、索引和已读状态。生产者提供来源资源名以及来源内稳定的条目 ID。相同的一对标识再次到达时，文章插件更新内容，保留文章名称和已读状态。框架登记来源关联并驱动执行。默认 rss.ingest 工作流连接两个插件，两者可以独立启停。

工作流为插件组织自身功能、复用其他插件的节点提供一种可选机制。插件可以直接调用业务服务，也可以定义、注册和更新工作流，由框架校验连线、构建执行计划并驱动运行。两种路径复用业务实现。

用户通过 CLI、GUI 或 API 操作订阅和文章。例如，用户选择“刷新订阅”，RSS 插件可以在内部调用抓取、解析和文章存储节点。业务入口应说明刷新结果或失败原因，用户无需认识节点、阅读执行计划或编辑图。框架的定义、编辑和检查接口面向插件开发与调试；通用工作流编辑器不属于面向用户的产品要求。

## 核心与节点库

| 部分 | 职责 |
| - | - |
| 业务模块 | 维护领域数据和业务约束，实现功能，注册可复用的节点与端口。 |
| 框架核心 | 维护通用数据关系、节点与连线声明、资源信息，生成并驱动执行计划，提供传输、同步依赖、扇出、反压与运行解释。 |
| 内置节点库 | 提供定时器、HTTP fetch 等通用组件，以及需要时的转换或信号辅助功能；通过与业务模块相同的注册机制接入。 |
| Host 与传输适配 | 组合模块，通过 CLI 和协议公开插件的业务操作。 |

定时器、HTTP fetch 等组件从核心执行规则中分离。核心不根据节点名称、RSS 类型、控制值或“是否幂等”标记推断业务行为。幂等、去重、重算和副作用处理由业务实现及其输入决定；核心不把某个布尔值转换成通用重试策略。

## 数据关系与处理关系

保留两类独立的通用关系：数据对象之间的关联，以及节点端口之间的处理连接。数据关联帮助模块引用或发现其他模块的数据；处理连接说明数据如何经过功能节点。业务字段及其不变量仍由模块维护，不把所有业务表压成统一文档模型。

数据对象身份、运行中的载荷引用、同步输入的消息键 各有用途，不默认互相等价。进程内可按只读约定共享对象引用，转换时产生新结果；跨进程、跨设备需要可传输的数据表示或可解析引用，不能直接传递 CLR 指针。当前 DataReference 只是数据身份，不是已经实现的分布式对象存储引用。

## 工作流的数据产出

插件决定哪些业务变更一起发布，并在同一数据库事务中写入。事务提交即产出，后续查询可读取整份结果，无需另设标记。插件及存储层负责回滚和核实提交结果，工作流按节点报告的结果推进。

同一次运行中，下游节点可以立即消费内存里的数据。例如，RSS 解析节点可以把文章草稿同时交给文章存储节点和其他插件。当前文章插件逐篇提交文章、索引和来源关联。刷新中断时，已提交的文章仍可读取。插件也可以按源提交，让同一次抓取的文章一起可见。两种粒度都符合工作流的产出约定。要在重启后继续处理同一份输入，还需能取得当时的内容和处理所需的上下文。[RSS 工作流](../../plugins/LazyTuiHub.Plugin.TuiHub.Rss/Backend/RssModule.cs) · [文章存储](../../plugins/LazyTuiHub.Plugin.TuiHub.Articles/Backend/ArticleStore.cs)

## 工作流、执行计划与运行记录

| 层次 | 内容与用途 |
| - | - |
| 逻辑工作流 | 插件为业务操作声明的节点、具名端口、连接和参数，表达期望的处理关系。 |
| 资源信息 | 各执行实例配置的资源及其可用条件，供计划判断和绑定；详细模型待定。 |
| 执行计划 | 将逻辑图结合当前资源，确定执行实例、资源绑定、传输路径和同步依赖，解释每一步如何执行。 |
| 运行记录 | 记录一次实际执行及其尝试、进度、等待、失败和结果，不把计划可行视为执行成功。 |

创建工作流时生成计划或给出无法形成可执行计划的诊断。执行工作流时结合当时的资源重新生成或确认计划，避免沿用已经失效的可用性假设。插件声明节点需要的资源，计划器负责安排必要的跨设备传输。

计划器检查连线、端口类型、结构依赖、资源绑定和传输条件。插件解释连线的业务含义。

校验反映规划时的可用条件。执行时，框架指出哪一步在等输入，哪一步因资源缺失、设备失联或节点失败而受阻。

## 面向公网设备的执行边界

MVP 由固定主节点生成和推进全部执行计划，调度所有任务。主节点安装部署支持的全部业务插件，在本机执行工作流，仅在本机无法执行某一步且允许降级时将该步委派给从节点。主节点离线时，系统不可用。账户服务独立管理身份和授权。各设备分别登记可用资源，参与执行的从节点必须与主节点安装完全相同的插件及版本。主节点按账户持久保存资源归属，设备离线时保留原绑定。目标行为与验收见[账户服务与权限 Note](2026-11-19-mvp-account-identity.zh.md) 和[多节点协调 Note](2026-11-19-mvp-coordination.zh.md)。

公网设备的资源和网络可达性各异。计划器按资源名和导出的包操作匹配设备。容量分配、数据保留和流的断点续传仍待细化。

对用户隐藏必要的数据搬运，不隐藏等待、传输失败或写入结果未知。远程超时不能证明操作没有发生；是否恢复或重试必须遵守节点的业务语义及现有协议约定。同步端口提供的逻辑依赖与成组交付，也不要求设备时钟一致或物理上同时收包。

工作流节点可在 `requires` 中声明额外需求，插件也可以在节点描述中声明必需资源。当前 Docker 原型中，各实例独立登记自己提供的资源，协调端使用已配置的对端地址和凭据查询清单。工作节点通过该接口报告已加载且允许导出的操作。每次生成计划时，框架合并需求，并与当时可达的实例清单、操作模式匹配。图中无需填写设备身份或传输步骤。

可重复的单流入、单流出转换优先使用满足条件的本地实例，同级远端按实例标识排序。不同包的输入可达性可能不同。发生可用性错误时才尝试下一个候选，遇到终止性拒绝或取消就停止。远端传输类型化数据及数据引用，本地调用沿用原对象。图、有限队列及同步组由协调端维护。

绑定所有者的包操作需要恰好一个满足条件的资源所有者。缺失或冲突时，计划说明原因。`articles.store` 要求 `workspace.primary`，协调端可以把写入发给远端主库。应用只发起一次写入，丢失确认时报告结果未知。所有者在同一事务内登记文章、来源引用及关联。Docker 原型依靠部署方为整个部署指定唯一主库，网络分区期间的可达清单无法证明全局唯一性。

## 可解释性与有限重放

框架应能解释计划中的放置、资源绑定、数据移动和依赖，以及运行中哪个节点正在做什么、等待谁、因何失败。运行身份、实际尝试和同步关联需要能与原工作流及计划对应，不只保留一条全图失败日志。

重放范围取决于实际保留的输入、配置、节点实现和状态。需要复现一次节点处理时，还应保留它实际消费的同步输入组，以及影响状态的输入消费顺序；不依靠全局时钟重建流与同步输入之间不存在的顺序承诺。

重新请求外部网站、当前时间或其他可变外部状态，不构成原输入的重放。涉及写入的重放仍由业务节点保证相应语义；记录一次运行不自动提供恰好执行一次或确定性结果。日志结构、保存介质、保留范围及恢复入口在实现时按具体用途细化。

## 借鉴范围

- [ComfyUI](https://docs.comfy.org/custom-nodes/backend/server_overview)：借鉴节点声明与自由连接的交互模型；本框架增加持续流动及明确的同步交付契约。
- [Ray Data](https://docs.ray.io/en/latest/data/key-concepts.html#operators-and-plans)：参考逻辑计划、物理计划和数据引用的分层，不照搬面向计算集群的对象存储与调度系统。
- [Flink](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/monitoring/back_pressure/)：参考持续数据流和反压；当前需求不引入其完整事件时间、状态后端或检查点体系。

## 可运行的实现与下一步

插件通过 NodeRegistration 声明任意数量的具名流式／同步端口和一个执行函数。宿主持有 NodeRegistry，供规划与执行使用。PipelineEdge 记录源节点、源端口、目标节点和目标端口。PipelinePlanner 检查端点、端口交付方式和类型严格一致性、输入生产者及当前后端要求的 DAG，生成绑定节点实现、连接和缓冲容量的 PipelinePlan；PipelineRunner 直接驱动这个计划。计划列出每一步的资源需求、候选实例和无法取得清单的对端。

创建／保存图时返回计划或可执行性诊断；保存允许保留缺失实现的定义，执行要求有效计划。运行图时重新生成计划，也可以直接运行已经生成的计划。CLI 的 plan 命令展示候选实例、端口及连接；--progress true 展示节点运行、同步等待、组就绪、完成和取消事件。包处理进度携带输入引用、尝试实例、结果和原因。运行历史尚未持久化。

Core 插件实现 `builtin.timer` 和 `builtin.http-fetch`。`LazyTuiHub.Nodes` 提供载荷类型及 `Source`、`Transform`、`Sink` 辅助方法。它们都注册普通框架节点。消费者声明具体的载荷类型，未使用的输出端口可以留空。

`WorkflowRuntime` 独立管理图的注册与存储。本地和 HTTP 刷新都调用 `rss.ingest`，文章保存在 SQLite 中。其他插件可以接收解析输出，也可以直接调用业务服务。[存储 Note](2026-11-17-mvp-storage-dao.zh.md) 说明 TTL、FTS5、原生连接和工作区事务的适用范围。

本轮通过 demo:workflow 演示未齐同步输入与流共存、成组配置更新及取消退出。节点执行 Note 记录目前采用的 key 配对、结束和暂存规则。Docker 场景覆盖非对称网络、逐源回退、资源撤回与新增，以及从远端向主库写入。活动计划内发现新成员、反馈图、跨设备同步端口、持久化运行历史和重放仍待实现。
