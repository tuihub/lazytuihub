# MVP 框架职责与执行计划

[English](2026-11-17-mvp-framework.en.md) | 中文

## 范围与维护

本 Note 记录框架的设计方向；[节点执行 Note](2026-11-17-mvp-node-execution.zh.md) 单独维护端口、同步交付、反压和节点状态；[插件 Note](2026-11-17-mvp-plugins.zh.md) 维护冷启动装配、元数据所有权及插件缺失时的无损边界。资源模型之后单独细化，目前不建立资源类型体系或调度策略。

[存储与 DAO Note](2026-11-17-mvp-storage-dao.zh.md) 维护所有 DAO 的三档访问、命名空间、托管模板、保留策略与需求匹配；其声明将成为计划资源绑定的依据，具体资源模型仍待讨论。

按照 [MVP 维护约定](../../AGENTS.md)，MVP 合入主分支前，所有 MVP 专题 Note 保持 proposed，允许随讨论和实现直接调整内容及组织，不因部分实现就冻结。原型代码、图定义、数据库 Schema 均无兼容承诺，目标是在 feat/mvp 分支形成干净、自洽的结果。每个 commit 同时提交可运行的代码增量和相应 Note 变更；已明确的契约严谨实现，未定细节先采用明确、可替换的简单行为，通过运行继续讨论。

本文同时维护目标设计与首轮本地实现。具名端口、同步输入对齐和本地执行计划已经落地；资源调度、远程执行和有限重放仍是设计目标。[运行指南](../../docs/development/streaming-mvp.zh.md) 描述实际可运行的版本。既有协议与仓库约定继续有效。

## 目标与应用边界

应用采用 C/S 单体结构，支持进程内低成本调用，以及跨进程、跨设备的常规 HTTP 通信；未来的 WebSocket 保留独立适配边界。沿用[协议基线](2026-11-15-protobuf-api-contract.zh.md)，业务逻辑由 C# 实现，生成覆盖契约和通信代码。工作流内部端口并不因此全部成为公开 API。

MVP 用 RSS 阅读器和 SQLite 探索框架与业务的分离。框架的价值是让不同模块注册的功能和数据能够连接与复用，而不是为 RSS 建立专用执行器。订阅、抓取、解析、落库、阅读和已读状态属于 RSS；通用数据关系、工作流结构、执行计划和运行驱动属于框架。

工作流是可选的组织方式。业务服务可以直接调用，也可以由节点适配后参与工作流；两种路径复用业务实现，不要求每个 API 或简单查询都经过工作流。工作流中的读取管线仍是有效用途，但不是阅读能力的前置条件。

## 核心与节点库

| 部分 | 职责 |
| - | - |
| 业务模块 | 维护领域数据和业务约束，实现功能，注册可复用的节点与端口。 |
| 框架核心 | 维护通用数据关系、节点与连线声明、资源信息，生成并驱动执行计划，提供传输、同步依赖、扇出、反压与运行解释。 |
| 内置节点库 | 提供定时器、HTTP fetch 等通用组件，以及需要时的转换或信号辅助功能；通过与业务模块相同的注册机制接入。 |
| Host 与传输适配 | 组合模块、暴露 CLI 和协议入口，将调用交给业务服务或工作流入口。 |

定时器、HTTP fetch 等组件从核心执行规则中分离。核心不根据节点名称、RSS 类型、控制值或“是否幂等”标记推断业务行为。幂等、去重、重算和副作用处理由业务实现及其输入决定；核心不把某个布尔值转换成通用重试策略。

## 数据关系与处理关系

保留两类独立的通用关系：数据对象之间的关联，以及节点端口之间的处理连接。数据关联帮助模块引用或发现其他模块的数据；处理连接说明数据如何经过功能节点。业务字段及其不变量仍由模块维护，不把所有业务表压成统一文档模型。

数据对象身份、运行中的载荷引用、同步输入的 messagekey 各有用途，不默认互相等价。进程内可按只读约定共享对象引用，转换时产生新结果；跨进程、跨设备需要可传输的数据表示或可解析引用，不能直接传递 CLR 指针。当前 DataReference 只是数据身份，不是已经实现的分布式对象存储引用。

RSS 的一次抓取可以连接定时器、HTTP fetch、RSS 解析和存储节点；其他业务可以接在解析输出上接收数据。这个连接不应要求修改 RSS 的业务实现或核心运行器。

## 工作流、执行计划与运行记录

| 层次 | 内容与用途 |
| - | - |
| 逻辑工作流 | 用户或模块定义的节点、具名端口、连接和参数，表达期望的处理关系。 |
| 资源信息 | 各执行实例配置的资源及其可用条件，供计划判断和绑定；详细模型待定。 |
| 执行计划 | 将逻辑图结合当前资源，确定执行实例、资源绑定、传输路径和同步依赖，解释每一步如何执行。 |
| 运行记录 | 记录一次实际执行及其尝试、进度、等待、失败和结果，不把计划可行视为执行成功。 |

创建工作流时生成计划或给出无法形成可执行计划的诊断。执行工作流时结合当时的资源重新生成或确认计划，避免沿用已经失效的可用性假设。用户不必在逻辑图中手工插入每一次跨设备搬运；执行计划负责暴露并安排必要的数据移动。

连接检查依据端口声明和类型一致性，不解释业务含义。计划层另外处理结构依赖、资源绑定和传输可行性；这不等于通过名称猜测某两个节点在业务上能否组合。

经过验证的工作流交给框架驱动。运行条件仍满足时推进；无法推进时说明具体原因，例如缺少资源、执行实例失联、输入未齐或节点失败。验证描述当时的可行性，不承诺资源和网络以后永不变化，也不把等待伪装成成功。

## 面向公网设备的执行边界

未来的执行实例可能拥有不同资源和网络可达性，通过公网协作；不假设它们处于低延迟、稳定互通的计算集群。资源配置和规则可以参与自动放置，但具体资源描述、选择算法、数据保存及断线恢复协议尚未确定。

对用户隐藏必要的数据搬运，不隐藏等待、传输失败或写入结果未知。远程超时不能证明操作没有发生；是否恢复或重试必须遵守节点的业务语义及现有协议约定。同步端口提供的逻辑依赖与成组交付，也不要求设备时钟一致或物理上同时收包。

MVP 先用本地实现验证这些职责边界，不预建完整分布式调度、共识、检查点或跨设备事务系统。

## 可解释性与有限重放

框架应能解释计划中的放置、资源绑定、数据移动和依赖，以及运行中哪个节点正在做什么、等待谁、因何失败。运行身份、实际尝试和同步关联需要能与原工作流及计划对应，不只保留一条全图失败日志。

重放范围取决于实际保留的输入、配置、节点实现和状态。需要复现一次节点处理时，还应保留它实际消费的同步输入组，以及影响状态的输入消费顺序；不依靠全局时钟重建流与同步输入之间不存在的顺序承诺。

重新请求外部网站、当前时间或其他可变外部状态，不构成原输入的重放。涉及写入的重放仍由业务节点保证相应语义；记录一次运行不自动提供恰好执行一次或确定性结果。日志结构、保存介质、保留范围及恢复入口在实现时按具体用途细化。

## 借鉴范围

- [ComfyUI](https://docs.comfy.org/custom-nodes/backend/server_overview)：借鉴节点声明与自由连接的交互模型；本框架增加持续流动及明确的同步交付契约。
- [Ray Data](https://docs.ray.io/en/latest/data/key-concepts.html#operators-and-plans)：参考逻辑计划、物理计划和数据引用的分层，不照搬面向计算集群的对象存储与调度系统。
- [Flink](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/monitoring/back_pressure/)：参考持续数据流和反压；当前需求不引入其完整事件时间、状态后端或检查点体系。

这些是设计参考，不是依赖选型或功能等价承诺。同步交付的具体契约以节点执行 Note 为准。

## 首轮本地实现与下一步

NodeRegistry 以统一执行函数注册任意数量的具名流式／同步端口。PipelineEdge 记录源节点、源端口、目标节点和目标端口。PipelinePlanner 检查端点、端口交付方式和类型严格一致性、输入生产者及当前后端要求的 DAG，生成绑定节点实现、连接和缓冲容量的 PipelinePlan；PipelineRunner 直接驱动这个计划。所有步骤暂时放在 local 实例，不建立虚构的资源清单或远程路径。

创建／保存图时返回计划或可执行性诊断；保存允许保留缺失实现的定义，执行要求有效计划。运行图时重新生成计划，也可以直接运行已经生成的计划。CLI 的 plan 命令展示本地放置、端口及连接；--progress true 展示节点运行、同步等待、组就绪、完成和取消事件。运行错误携带节点身份和原因，尚未持久化运行历史。

通用定时器、HTTP fetch、相应载荷及常见流式节点注册辅助位于独立的 LazyTuiHub.Nodes 节点库，核心不引用它。Source、Transform、Sink 是库中单流模式的便利封装，最终均注册为同一种核心节点。输出消费者按实际载荷类型注册，不使用 object 可赋值连接绕过严格类型契约。未连接的输出可以留空，支持模块声明并非每张图都会使用的分支。

RSS 已迁移到新端口与计划模型，本地／HTTP 调用、SQLite 工作区和解析后跨业务分支继续运行。Core、RSS 和 SQLite 存储提供者已通过可信冷启动 DLL 插件加载；插件 Note 记录归属保留、可用性诊断、元数据事务协调及显式 hook。WorkflowRuntime 独立于 RSS 管理图注册和存储。当前直接业务操作仍通过工作流调用；解除这层强制依赖留待后续迭代。DAO 工具包已区分通用记录／TTL、SQLite 专用 FTS5 及原生连接访问。插件传入命名空间表目标，以声明能力控制激活，以显式持久委托授权清理。RSS 明细默认长期保留；持久输入、重放占用及跨存储协调仍在存储 Note 中待定。当前仅实现 SQLite，不新增数据库 Schema 规范或旧图／旧 Schema 迁移层。

本轮通过 demo:workflow 演示未齐同步输入与流共存、成组配置更新及取消退出。节点执行 Note 记录目前采用的 key 配对、结束和暂存规则。资源模型、循环图及反馈、跨设备协议、运行记录存储和有限重放入口仍需细化；它们不作为已实现能力或额外兼容承诺。
