# MVP account service, trusted identities, and access control

English | [中文](2026-11-19-mvp-account-identity.zh.md)

## Identities for each call

Every installation runs a client and a server in the same process. The client can call a local or remote business service directly. The fixed primary's account service issues, verifies, and revokes identities and maintains account ownership and URI grants. It alone accesses credential tables and issuance keys. The primary's coordinator, business plugins, and other devices follow the same trust boundary.

| Call | What the recipient verifies | Example |
| - | - | - |
| Client → local or remote server | User session, intended service, permission checked with the freshness required for the operation, and account ownership | A user reads their articles directly from C. The client installation needs no device enrollment. |
| Server → remote server, acting as a device | Device credential, active registration, and permitted operation. Task claims also require the assigned target and attempt. | B reports resources, claims work, and submits results to the primary. |
| Server → remote server, acting for a user | Device identity, the user's grant to that device, target service, and operation. Audit records identify both parties. | A user authorizes B to read articles from their account on C on a schedule. |

User sessions, device credentials, and user grants have separate storage and lifetimes. Each caller chooses its credentials for the operation. In-process calls can pass an account-service-verified context directly and apply the same authorization checks as HTTP. Desktop, CLI, plugins, and background work follow that rule. A shared process, local address, or relay conveys no authority. A primary that supplies execution resources enrolls its execution side. A schedule records the acting principal and account so each dispatch can recheck permission. An assignment authorizes its device, account, operation, and attempt. Task payloads carry no user session credentials. [NIST zero trust architecture](https://csrc.nist.gov/pubs/sp/800/207/final) · [Coordination Note](2026-11-19-mvp-coordination.en.md)

## User provisioning and session issuance

When the primary initializes the account store, it reads the initial administrator's username and secret from deployment configuration, creates the user through ASP.NET Core Identity, and grants the initial system administration permissions. The user, initial grants, and initialization marker commit together. Subsequent starts preserve the stored password and grants, including after an administrator is disabled. A protected file or environment can supply the initial secret. Administrators with the user-creation permission provision all further users. The MVP exposes no self-registration endpoint. Assigning administrative permissions requires a separate authorization decision.

The official CLI and desktop client can open a first-party session over HTTPS with the primary account service. For example, the CLI prompts for a username and a password with terminal echo disabled, verifies the configured primary, and sends the login request directly to it. The primary uses ASP.NET Core Identity to verify the account and password, applies the relevant sign-in restrictions, and issues a revocable user session. A business worker receives only a credential intended for its service. Only the primary receives the password. First sign-in requires neither a browser, a second device, nor device enrollment. The official CLI and desktop client are already trusted parts of the product. In direct sign-in they receive the password and send it to the primary for verification. With a system browser, the primary's login page receives the password and the client obtains the authorization result. The project owns first-party session issuance, expiry, renewal, and revocation. Identity supplies password hashing. The ASP.NET Core IdentityV3 format uses PBKDF2-HMAC-SHA512, a 128-bit random salt, a 256-bit derived key, and 100,000 iterations by default. [OpenBao username/password login](https://openbao.org/docs/auth/userpass/) · [Argo CD local and SSO login](https://argo-cd.readthedocs.io/en/latest/user-guide/commands/argocd_login/) · [Identity password hasher](https://github.com/dotnet/aspnetcore/blob/v10.0.15/src/Identity/Extensions.Core/src/PasswordHasher.cs)

OAuth can also serve clients and services within one product. Authorization code with PKCE keeps passwords on the primary's login page. RFC 8628 supports approval on another terminal. These options suit a common sign-in page, external identity providers, or explicit delegation. A first-party application session is a separate candidate and does not use the OAuth password grant. The IETF first-party applications draft introduces a native authorization challenge endpoint and leaves authentication steps to the deployment. It has yet to become an RFC. Kerberos V5 is a mature centralized authentication standard that lets a client present a ticket to a particular service. Adopting it requires operating a KDC and managing service principals, keys, and clocks. Device admission and business permissions would still need product rules. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4) · [IETF first-party applications draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-first-party-apps/) · [Kerberos V5](https://www.rfc-editor.org/rfc/rfc4120.html)

Use Proto for product-defined login, provisioning, device enrollment, and business operations. Where OAuth is chosen, OpenIddict can serve its standard endpoints. The same account service verifies users and permissions for first-party sign-in and device delegation. [API development guide](../../docs/development/api-design.en.md)

## How workers check permissions

Normal operation requires a reachable primary, which owns session, device, grant, and permission state. Device approval, permission changes, and new assignments use current state on the primary. A waiting poll rechecks before delivering work. Local steps and stream records use the assigned attempt's authority. Workers request authorization decisions on demand and may reuse allow decisions while valid.

The primary keeps an instance identifier and a global revocation sequence. It advances the sequence as part of committing any change that can invalidate a cached allow decision, including session revocation, device deactivation, a narrower delegation, or removal of a permission relationship. User provisioning, new sessions, and changes that only extend permissions leave the sequence in place. An authorization response carries the instance and sequence of the state used to evaluate the decision. Existing coordination heartbeat responses also carry both values.

Workers cache allow decisions by credential, account, target service, resource URI or access scope, and read/write mode. Delegated calls also bind the device certificate and grant. On a cache hit the recipient checks the instance, latest known sequence, expiry, current object's account, and the credentials actually presented. It requests a fresh decision on a cache miss, an older sequence, or expiry. A worker advances its sequence within an instance and requests a fresh decision when an authorization response arrives with a sequence older than it has already seen. It clears the cache on reconnect or a primary instance change and fills it again as requests arrive.

Heartbeat intervals and concurrent request timing between a committed change and its observation count toward the revocation delay. Each decision has its own expiration, bounded by the relevant credentials and grants. Heartbeats do not renew existing decisions. If the primary is unreachable and the worker has no usable decision, it reports that the authorization service is unavailable. Set lifetimes and connectivity failure criteria during product implementation. [RFC 7662 caching trade-offs](https://www.rfc-editor.org/rfc/rfc7662.html#section-4) · [Coordination Note](2026-11-19-mvp-coordination.en.md)

## Credential custody

The client holds its user session, the device server holds its device private key and delegated credentials, and the primary account service holds issuance keys. Platform stores, persistence locations, backup, and recovery remain open.

## Administrator-approved device enrollment

1. The worker's server generates an ECDSA P-256 private key locally, signs a PKCS#10 request with SHA-256, verifies the configured primary over HTTPS, and submits the request. The account service verifies the CSR signature and public key and binds that key to the pending request. It returns a private random pickup credential, a human-readable pairing code, a verification address, and a polling interval. It stores a digest of the pickup credential, expires pending requests, and limits guessing according to the display code's entropy. The private key stays on the device.
2. An administrator uses a signed-in client to compare the code and public-key fingerprint displayed by the device. The account service checks write access on the device approval control URI and records the approver and decision. On approval, the issuer assigns a stable device ID, issues an X.509 certificate for TLS client authentication, and records its fingerprint and status. The issuer selects the subject, usage, and extensions from its own profile. One approval creates one device identity.
3. The worker polls with the private credential. It observes backoff while pending and receives explicit denial or expiry outcomes. The authority persists the issued result so repeat collection with a valid receipt returns the same ID and certificate. The device proves key possession through mTLS. Each claim, including delivery after a long poll, still checks active registration. Renewal uses a valid device credential and a new CSR. A lost key requires fresh approval. Diagnostics and task payloads exclude pickup secrets and private keys.

Use .NET's `CertificateRequest`, Kestrel, and ASP.NET Core Certificate Authentication. The project owns pending requests, the device registry, and idempotent issuance. Kubernetes separates a node's certificate request, approval, and signing. EST specifies how a requester can retry after manual approval. Administrator approval admits a device to the system. A user may subsequently grant it access. [Kubernetes node bootstrapping](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-tls-bootstrapping/) · [EST deferred approval](https://datatracker.ietf.org/doc/html/rfc7030#section-4.2.3) · [ASP.NET Core certificate authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/certauth)

## A device acting for a user

The user confirms the device, account, business capabilities, and permitted read/write modes at the primary. The account service records the grant, expiry, and revocation state and issues a separate user access token to the device. The token identifies the user as its subject. The RFC 8705 `cnf.x5t#S256` confirmation binds it to the device certificate. The device presents both to the target service. The recipient checks active device registration, token audience, certificate binding, and the live grant, then applies the user's current permissions and resource ownership. An ordinary user token and a valid device certificate do not establish a grant. Revoking the grant ends that delegation while the device can still claim work in its own right. Another certificate cannot present the old token after device deactivation or key rotation. [RFC 8705 certificate binding](https://www.rfc-editor.org/rfc/rfc8705.html#section-3) · [OpenIddict mutual TLS](https://documentation.openiddict.com/configuration/mutual-tls-authentication)

Devices with a usable callback can use authorization code with user consent. A headless device can consider RFC 8628 so the user can sign in and approve the delegation on another terminal. OpenIddict 7.9's built-in PKI client authentication also requires the device certificate to match a host in the OAuth client's registered redirect URIs. For devices without callbacks, a candidate is to use the library's certificate validation extension point to verify the registered OAuth client, device ID, certificate, and valid chain. This path needs its own verification. The HTTPS listener for user calls accepts clients without certificates. Device-authenticated requests use a separate listener or TLS hostname. The same business operation authorizes the resulting call context. [RFC 8628 device authorization](https://www.rfc-editor.org/rfc/rfc8628.html) · [OpenIddict certificate validation source](https://github.com/openiddict/openiddict-core/blob/7.9.0/src/OpenIddict.Core/Managers/OpenIddictApplicationManager.cs)

## Hierarchical URI authorization on the primary

### Resources and grants

The primary's account service holds account and device ownership records and explicit URI grants. Data, operation endpoints, and authorization settings use the same ACL. A grant identifies a principal, resource URI, and access mode. Read and write are independent, so job submission can be write-only. Reads, listings, and searches reveal only readable resources. When a write is denied, read access determines whether the response may reveal that the resource exists.

A user ID identifies the actor. An account ID scopes business data. Personal account owners can read and write their own business resources by default. Sharing adds explicit grants for other principals. Authorization settings use their own URIs and inheritance boundaries. In the initial release, account and device owners manage the corresponding grants. System control URIs govern operations such as account provisioning and device approval. Future group grants can use the same URI permissions.

A business plugin uses the plugin ID established at load time as its URI namespace and defines the resources and read/write semantics within it. The implementation uses `lazytuihub://<plugin>/accounts/<account>/<collection>/<id>` for account data. Grants cover complete URI segments. The account service validates canonical segment encoding before storing grants. Account and device owners manage sharing through `core/accounts/<account>/grants` and `core/devices/<device>/grants` in the same scheme. The separately granted device job URI is `core/devices/<device>/jobs`. Plugins resolve ordinary references and separately check the target URI. Business identity and account ownership identify data resources and let their grants survive a change in hosting device. [Plugin identity and resource namespaces](2026-11-17-mvp-plugins.en.md)

### Device capabilities and user delegation

A device registration records its owner. The owner can use the device by default and can grant others access to its capabilities. Direct calls and planner placement both check the same URI when the acting principal uses such a capability, for example write access to the device's job endpoint. The device's exports define available operations. Access to business data on a device checks the data URI, while the resource binding determines where to execute. An enrolled device uses its identity to report inventory, claim work, and submit receipts to the coordinator. [Coordination Note](2026-11-19-mvp-coordination.en.md)

Delegation specifies the account, business capabilities, and read/write modes. For a delegated call, the framework intersects the user's rights and the delegation's scope on each URI the operation uses. Assigned work also observes the current attempt's target and operation. A device-use grant authorizes a principal to use a device capability. A user delegation authorizes a device to call resources on the user's behalf.

### Shared authorization and plugin data access

The framework checks URI access individually or in batches and can return the effective permissions of the current call within a requested resource scope. The plugin chooses that scope for the operation. It can query relevant resources across plugin namespaces. Credential checks, URI ACL evaluation, delegation, and caching of allow decisions share one implementation. The primary checks resolved URIs while plugins locate and interpret business objects where their data resides.

The plugin uses the trusted account scope and the object's ownership to resolve the target URI and keeps actual reads and writes within that grant. For an article request containing only an article ID, the plugin resolves the target in the trusted account and applicable business scope. When a shared feed also grants access to its articles, the plugin confirms the actual relationship and checks the URI used for that access. HTTP, CLI, desktop, and workflows use the same application-service rules.

The plugin passes the trusted account ID and the authorized object or collection to its DAO. Single-object queries and updates apply both conditions. Listings and full-text searches filter by visibility before paginating. Object IDs and cursors resolve within their account and query scope. The framework returns a decision or access scope. The plugin applies it to queries, indexes, and mutations, with reusable helpers available from DAO providers. [DAO and business storage boundaries](2026-11-17-mvp-storage-dao.en.md)

Subscription URLs and idempotency keys are unique within each account in shared SQLite. The RSS and article plugins apply account and URI visibility to business reads and writes, including article full-text search. Subscriptions, articles, fetch details, and data relations carry the account scope. Workflow definitions remain shared installation metadata in this increment. User-owned workflows and durable run records belong to the coordination design. [Subscription store](../../src/LazyTuiHub.Rss/RssStore.cs) · [Article store](../../src/LazyTuiHub.Articles/ArticleStore.cs)

## Implemented scope and remaining acceptance

The primary implements first-party HTTPS login with ASP.NET Core Identity password hashing, random bearer sessions with only their digests persisted, and explicit logout. Users after bootstrap are created by an administrator on the primary. The CLI can sign in to the remote primary without a browser and accepts a session for local commands. The desktop can start with a supplied local session. Both local and remote operations use the same plugin authorization. The configured default session lifetime is eight hours, covering one workday. A fresh workspace is required for this MVP schema.

The coordinator evaluates current URI grants when creating a plan and again before dispatch. Account mode uses the existing push transport and its configured peer credentials. Workers accept the coordinator's account scope and limit execution to the local operation's declared resource access. Account mode runs RSS on explicit refresh until schedules can carry a verified actor. Device enrollment, certificate-bound user delegation, worker allow caching, user and permission groups, and durable pull coordination remain open. [Primary and worker integration test](../../tests/LazyTuiHub.Tests/AccessTests.cs)

A separate OpenIddict 7.9.0 probe on two HTTPS listeners exercised authorization code with PKCE, token revocation, group removal with an existing token, administrator approval of a CSR, repeated pickup of the same device identity, mTLS, and deactivation on an existing connection. Bound tokens required the enrolled certificate. Revoking delegation left device-only task claims available. The experiment used a registered callback and programmatic consent.

Verify the following through product entry points in the next increment.

- The same user obtains the same access decision locally and remotely. A client on an installation that has never enrolled as a device can reach a remote business server directly. Enrolled installations can also use the user session on its own. Delegated calls identify the user, device, and grant. Device identity alone cannot read user articles.
- Initial administrator configuration applies once. Administrators add all further users. Ordinary users cannot approve devices. Denial, expiry, repeat pickup, and revocation yield distinguishable outcomes. Online decisions and new dispatches reflect removed permissions immediately. Paging within the same valid scope must not add an authorization request to the primary for each page. Grant-only changes preserve existing allow decisions. After observing a revocation sequence, the worker must reject old decisions and delayed authorization replies for new requests. Verify on-demand cache rebuild after reconnect and primary instance changes.
- Exercise first-party CLI password sign-in, direct business service access, loss and restoration of primary connectivity, and certificate rotation with separate primary and business servers. If OAuth is selected, verify its callback or cross-device confirmation and separately exercise headless device delegation.
- Two accounts in one SQLite database can use the same URL and idempotency key. Authorization and article queries use the same account and object scope. Read-state changes, searches, pagination, and attempt IDs observe that boundary as well. Personal account owners get business data access by default. System administrators use the corresponding resource grant to read another account's data.
- Device use can be granted and revoked independently. A user with device-use access alone can submit permitted tasks. Reading someone else's data or changing device grants requires authorization on the corresponding URI. A write-only job endpoint accepts submissions and checks reads against their own grants.
