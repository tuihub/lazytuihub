# GitHub CI checks

English | [中文](2026-11-16-github-ci.zh.md)

## Status and scope

This Note plans GitHub Actions quality checks for the current main-branch commit snapshot, reusing the [repository baseline](2026-11-15-repository-initialization.en.md), [C# lint](2026-11-15-csharp-lint.en.md), and [protocol and generation baseline](2026-11-15-protobuf-api-contract.en.md). Scope is CI only. Dependency updates, releases, website deployment, collaboration templates, and repository rules are separate discussions.

CI and CodeQL workflows and local check entry points have been written. Local validation does not establish that GitHub Actions has run. This Note remains proposed pending real main events and runner validation.

CI is responsible for the main branch's deliverable state. Local checks, development branches, PR commit preparation, and agent decision processes retain their respective agreements and are outside this CI's verification scope.

## Trigger and check target

Both CI and CodeQL run only on pushes to main, checking out the exact commit identified by the event. A later main update does not change the commit already under examination. Event semantics follow the [official GitHub reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Check whether that commit's code, declarations, configuration, derived artifacts, and documentation are consistent, buildable, and compliant with existing quality agreements. Report the actual commit, platforms, and results without reconstructing the development process.

CI does not validate PR titles, every development-branch commit message, or whether local hooks ran, and does not run cross-commit Note lifecycle gates. The Markdown pipeline still validates current Note metadata, references, and structure. Main-branch Conventional Commits and Note lifecycle agreements remain enforced through local tools and review.

## Reuse tasks and platforms

Execute shared tasks from [mise.toml](../../mise.toml) without rewriting their rules in workflows. check:ci aggregates snapshot checks, workflow validation, tooling tests, and API calling verification without local commit-message or Note-history gates. Local `mise run check` retains its complete default behavior.

| Group | Platforms | Work |
| - | - | - |
| quality | Linux | check:ci covers files, Markdown, C#, APIs, actionlint, product tests, and existing tooling tests; demo:api already includes check:api. |
| platform | macOS, Windows matrix | build and demo:api verify the same commit's build and calling pipeline on the other two modern systems. |
| CodeQL analyze | Linux, separate C#, JavaScript/TypeScript and Actions entries | Default queries cover the built solution, helpers and workflows and upload Code Scanning results. |
| Result display | Native GitHub run results | No separate summary job; retain each job and matrix entry's success, failure, or cancellation. |

test:tools uses Node's built-in runner for existing `.agents/tests/*.test.mjs`, already including test:lint's files without repeating that group. These tests validate tooling rather than audit this development process. The test task runs the xUnit product-test executable, covering pipeline execution, RSS, SQLite, and local/HTTP behavior using temporary workspaces and local fixtures. Product tests retain their existing separation from product analyzers.

Initially check the complete current main snapshot, concentrating platform-independent checks on Linux and reserving other runners for builds and calling verification with platform value. Do not build an affected-dependency graph yet, require this matrix for every local edit or development-branch push, or add a daily-full-run policy.

## Tools and execution environment

Use the maintainer's [mise-action](https://github.com/jdx/mise-action) to prepare GitHub-hosted runners. Existing authoritative declarations supply the SDK, Node.js, pnpm, C#, and protocol tools rather than duplicated workflow versions. mise also pins the added actionlint tool; check:workflows validates Actions syntax, expressions, and job configuration. After reviewing provenance, permissions, and maintenance cost under the [repository defensive-posture agreement](2026-11-16-defensive-posture.en.md), checkout, CodeQL, and mise-action follow their maintainers' major-version tags rather than a blanket SHA-pinning policy without concrete justification.

Explicitly install required tools, install dependencies with frozen-lockfile, restore local .NET tools, and run setup:aip for the official originals at the adopted commit. Doctor remains diagnostic. Checks read source and derived artifacts; CI does not repair, recommit, or relax the 1 MiB file limit.

Ordinary CI uses contents:read without persisted checkout write credentials, repository secrets, or privileged events. CodeQL separately receives security-events:write for result upload and actions:read as required by the official template for private-repository run information. Ordinary CI does not receive these permissions. Pass event values as data or safe arguments rather than inserting them into shell source. See [GitHub's security guidance](https://docs.github.com/en/actions/reference/security/secure-use).

## CodeQL coverage and compatibility

The [CodeQL Action](https://github.com/github/codeql-action) uses default queries for each language. The JavaScript/TypeScript and Actions jobs use [.github/codeql/config.yml](../../.github/codeql/config.yml) to scan helpers and workflows. For C#, mise installs the SDK pinned in the repository. CodeQL traces a clean build of `LazyTuiHub.slnx` to include compiled and generated sources. C# 14 and .NET 10 are within the [official support table](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/). The runner must complete extraction, analysis and upload before the scan can be considered verified.

GitHub Code Scanning requires an eligible repository and appropriate permissions; see the [official availability guidance](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning). Without remote repository context, account features, SARIF upload, and remote scan results remain unverified.

## Information boundaries and execution cost

CI relies only on the checkout, execution results, and obtainable event data. It cannot know developers' uncommitted worktrees, pre-commit intermediate states, proposed states never committed, or whether semantic review happened. Do not create gates or process sidecars for those facts.

Current-snapshot checks do not depend on complete Git history, the pre-push commit, or PR history. Initial pushes, history rewriting, and read-permission limits must not fail merely because that information is missing. Actual tool, dependency, or command errors in required checks remain failures.

Cancel runs superseded by newer main commits to save resources. The new run still checks the full snapshot, preventing coverage gaps after earlier cancellation. Cache only tool and dependency acquisition, keyed by platform and authoritative configuration. Execute checks on cache hits rather than caching success or substituting older generated output for comparison.

Observe cold-start and cached durations before optimizing caches, task groups, and execution budgets. Future change-based selection must use a verified main-branch baseline; uncertain impact falls back to checking the full current snapshot. This Note adds no product-test duration or coverage thresholds.

## Implementation and acceptance

Shared entry points stay in mise without new development-process validators or changes to local task defaults.

Local acceptance runs check:ci, check:notes, and check:commit, covering snapshot tasks and retained local agreements respectively. After confirming the target GitHub repository and Actions availability, validate Linux checks, both platform builds and calls, CodeQL language coverage, and result upload on a real main push. Existing negative tests continue to establish compilation, generation, and file-limit gates; local success does not replace remote runner validation.

Local task success, parseable workflow syntax, or committed configuration does not establish active remote CI. Move this Note to implemented once real main events and platform results are verifiable. This scope reports main-branch quality; pre-merge protection and remote repository rules are outside this configuration.
