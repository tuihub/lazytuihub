# MVP 节点端口、同步交付与状态

[English](2026-11-17-mvp-node-execution.en.md) | 中文

## 范围与状态

本 Note 维护[框架设计](2026-11-17-mvp-framework.zh.md)中的节点执行契约。按照 [MVP 维护约定](../../AGENTS.md)，合入主分支前保持 proposed，可直接修改。首轮实现已替代原单流运行器；下文区分目标契约与当前的简单规则。[WorkflowDemo](../../src/LazyTuiHub/Examples/WorkflowDemo.cs) 是可运行示例。

## 节点与端口声明

模块为节点声明名称、任意数量的具名输入／输出、端口类型和执行函数；每类端口均可以为零，不设置固定端口数上限。源、转换和消费行为由端口组合表达，不要求三套独立的节点执行机制。

端口分为流式和同步两种交付方式，输入与输出都可声明。原来讨论的“控制信号”属于同步数据的一种业务用途，不再作为核心中的第三类端口。同步数据同样可以是配置、计算结果或对象引用，核心不识别其业务含义。

连接依据端口声明及数据类型一致性建立，替换原型的 CLR 可赋值关系检查。端口交付方式也属于声明，供计划安排传输和依赖。核心不根据名称、布尔值或业务类别推测如何转换、组合、去重或重试。

| 契约 | 流式端口 | 同步端口 |
| - | - | - |
| 交付 | 数据可用时尽快交付，遵守反压和资源条件。 | 按 messagekey 满足依赖、等齐输入，成组交付。 |
| 时序 | 不承诺业务处理顺序或不同流之间的顺序。 | 保证同一次关联计算中的声明依赖顺序。 |
| 读取 | 节点自行决定如何消费各路输入。 | 节点一次取得完整的同步输入组。 |
| 主要成本 | 传输、队列和缓冲。 | 另有对齐等待及未齐输入的暂存。 |

某个本地队列采用 FIFO，不会自动成为所有流的端到端顺序承诺。流式交付的“尽快”也不取消反压或构成实时延迟保证。

## 同步交付

messagekey 标识需要关联的一次计算。框架根据声明与执行计划确定参与的同步输入端口，按 key 收集输入；所需输入齐备前，节点不能提前消费其中一部分；齐备后通过一次读取取得整组输入。

```text
A(k) 到达 → 框架等待
B(k) 到达 → 节点一次取得 { A(k), B(k) }
```

“同时到达”是节点观察到的逻辑成组交付，不是不同线程或设备在相同物理时刻收包。分别向多个独立队列写入，并不足以建立这个契约；端口包装必须提供整组读取。

同步输出满足后继的声明依赖，后继在自己的同步输入齐备后取得输入。依赖之外的节点及不同 key 不因此获得全局串行顺序。messagekey 用于关联，不自动成为业务幂等键。跨生产者的重复消息、多轮计算及一对多关联仍需细化；本轮仅在相同 key 内按每个端口的接收顺序配对，不将其宣称为业务上的正确轮次关联。

同步依赖不会隐式扩展到流式端口。配置先发送不证明某条流消息必定采用该配置；完成信号到达也不证明另一条流已被消费完。需要这些关系时，节点明确绑定配置引用，或在相应处理完成后发布同步输出。核心不从名称推断流与同步数据之间的时序。

参与输入缺少结果时，必须区分等待、明确无结果和失败。当前暂以等待和生产者结束后的失败表达未齐输入；通用“本次无结果”表示尚未实现。框架不把未到输入自动补成默认值；运行解释指出等待哪个端口和 key。取消或实际失败应能结束相应等待，不设定任意超时或静默丢弃策略。

## 持续执行与状态更新

C# 可以让一个长期运行的异步执行函数持续处理这两类输入，流数据到达和完整同步组就绪均可唤醒节点。框架提供有类型的读写及多输入等待包装，节点决定如何读取、组合、发布，以及何时修改自己的状态。“同步”描述可见性和依赖，等待仍可以异步进行，不要求阻塞线程。

建议先采用单一逻辑执行流独占节点状态，示意如下：

```csharp
public async Task ExecuteAsync(NodeContext context, CancellationToken ct)
{
    var options = (Factor: 1, Offset: 0);
    await foreach (var input in context.ReadEventsAsync())
    {
        if (input is SynchronizedInput sync)
            options = (sync.Get<int>("factor"), sync.Get<int>("offset"));
        else if (input is StreamInput data)
        {
            var snapshot = options;
            await context.WriteAsync("result", data.Get<int>() * snapshot.Factor + snapshot.Offset, ct);
        }
    }
}
```

SynchronizedInput 表示包含 factor 与 offset 的完整同步组；StreamInput 保留端口与载荷。ReadEventsAsync 使用运行器绑定的取消令牌，不需要启动并遗弃多个竞争读取，也不引入跨类别的业务时序承诺。

配置更新通过替换局部状态影响后续开始处理的数据。一次处理取得不可变快照后，当前处理和输出期间到达的更新先等待，循环消费更新后才影响后续消息。初始配置可以由节点提供默认值，也可以由节点先等待配置后开始消费数据。

若同步输入需要影响正在处理的数据，节点必须明确更细的生效点，例如逐块读取状态或通过取消令牌协作退出。并行处理流数据时，可使用不可变快照和明确的共享状态协调；这不是核心必须默认启用的并发策略。节点负责状态作用域、配置切换、信号边沿和重复脉冲的业务含义；通用辅助可放入节点库。

节点实际消费输入的顺序决定上述局部状态变化，不依靠发送时间推断哪条流消息应用哪个配置。强绑定需求应以明确关联或配置引用表达；需要重放时，保留实际消费输入及必要的顺序，参见框架 Note。

## 传输、扇出与反压

框架提供流的异步装箱与端口包装，节点面向稳定的读写抽象，不直接依赖具体 Channel，便于以后绑定远程传输。可使用 [.NET Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels) 和异步枚举实现本地后端；普通 Channel 的多个消费者竞争取值，核心扇出需要向各分支分别交付。

本地扇出可让分支按只读约定共享同一载荷引用。缓冲满时异步等待并传播反压，不通过静默丢弃实现“尽快到达”。同步输入暂存同样消耗资源，后续预算应根据真实成本决定，不在本 Note 固定条数、大小或保留时间。慢分支的隔离策略仍待具体需求决定。

多路等待应封装读取就绪或妥善管理挂起读取，避免反复开启读取后丢弃未胜出的任务，导致消息被无人处理的读取取走。取消、输入结束和错误也需要穿过端口包装，而非只传输成功的数据。

共享对象引用只降低本地传输开销，不建立跨设备共享内存。远程传输必须维护同步组的身份与完整性，仍不能依赖网络到达时间构造同步语义；相关协议另行设计。

## 首轮简单规则与验证

节点所有声明的同步输入组成一个参与组，每个输入必须有生产者。同步输出显式传入 messageKey，接收端按原字符串对齐；核心不自动生成或从持久数据身份推导 key，节点需要继续关联时显式转发。每个 key 的各端口维护 FIFO，同组各取一个值；同 key 可重复形成多组，不将重复 key 自动去重。多个生产者向同一端口供数时，按实际接收顺序配对；不同 key 按齐备情况推进，不承诺全局顺序。

一个端口在所有上游生产者结束后关闭。当某个待齐组缺少已经关闭的端口，立即以节点、key 和缺失端口解释失败，即使其他流仍开放，也不永久等待。尚有可能到达的输入保持等待；取消会中断队列读写及节点协作等待。节点函数返回即停止接收后续输入，上游继续写入会得到关闭错误，避免在无人消费的满队列上挂起。正常消费节点应处理输入到结束，或显式安排取消。

每节点有界入口采用图中 bufferCapacity，默认沿用 16；满时等待，扇出暂时顺序交付，所以慢分支会反压上游。未齐同步值移入内存暂存表，不计入入口容量；当前没有暂存数量或整个进程的字节预算，也未实现落盘。不能将有界入口宣称为整体内存有界，资源预算及慢分支隔离留待后续迭代。

运行器发布 running、waiting-synchronization、synchronized、completed、canceled 事件，等待信息包含 key 和缺失端口；这只是本地进度回调，尚无持久重放日志。demo:workflow 用显式确认协调示例输入，验证流在同步未齐时使用初始参数，随后完整配置让输出依次为 2、7、13，最后取消所有运行任务。示例协调不构成流与同步输入之间新的框架时序保证。

产品测试覆盖异 key 交错、同 key 多轮、关闭端口导致无法补齐、未齐组取消、类型／交付方式／端口名称不匹配，以及提前退出消费者解除上游等待；原来的广播、反压、合流、失败取消、RSS 和 HTTP 场景同步迁移。

完整检查暴露了多个 .NET 任务并行写入共享构建产物的问题。测试和示例任务通过 mise 的 [wait_for](https://mise.jdx.dev/tasks/task-configuration.html#wait-for) 等待同次运行中较早的构建任务，不为单独调用增加额外前置检查。现有检查全部保留。

## 后续边界

本次支持流式交付与按 key 同步交付共存。全批封口、阶段物化、整批完成屏障、批执行模式、窗口或水位线不属于当前需求。

参与组的进一步声明方式、自动 key 传播、多轮／一对多的业务关联、无结果表示，以及依赖环和反馈仍需细化。当前简单选择不是永久契约；状态示例也不建立并发、优先级或公平性承诺。资源与远程恢复继续按框架 Note 的边界讨论。
