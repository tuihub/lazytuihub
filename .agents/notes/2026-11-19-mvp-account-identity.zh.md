# MVP 账户服务、可信身份与权限

[English](2026-11-19-mvp-account-identity.en.md) | 中文

## 一次调用可以使用哪些身份

每个安装都在同一进程中运行 client 和 server。client 可以直接访问本地或远程业务服务。固定主节点的账户服务统一签发、验证和撤销身份，维护账户归属和 URI 授权。只有它可以读取凭据表和使用签发私钥。主节点上的协调器、业务插件和其他设备同样受这个边界约束。

| 调用 | 接收端验证 | 示例 |
| - | - | - |
| client → 本地或远程 server | 用户会话、目标服务、按操作要求取得的用户权限和账户归属 | 用户直接连接设备 C 阅读自己的文章，安装 client 的机器无需登记为设备 |
| server → 远程 server，以设备身份工作 | 设备凭据、当前登记状态和操作范围。领任务时另核对派发目标和尝试 | B 向主节点报告资源、领任务和回报结果 |
| server → 远程 server，受用户委托 | 设备身份、用户授权给这台设备的凭据、目标服务和操作。审计同时记录用户与执行设备 | 用户授权 B 到 C 读取其账户下的文章，B 定时执行 |

用户会话、设备凭据和用户委托分别保存，调用方按用途选择。进程内走同一套权限判断，可以直接传递账户服务验证过的调用上下文。桌面、CLI、插件及后台任务都遵守这个约定。同进程、本机地址和中继连接均不授予权限。主节点若提供执行资源，其执行端也要登记。定时任务保存运行主体和账户，每次派发重新核对权限。领取任务授予的能力只覆盖指定设备、账户、操作和尝试，任务载荷不携带用户会话凭据。[NIST 零信任架构](https://csrc.nist.gov/pubs/sp/800/207/final) · [多节点协调 Note](2026-11-19-mvp-coordination.zh.md)

## 用户开户与会话签发

主节点首次初始化账户库时，从部署配置取得首位管理员的用户名和初始秘密，通过 ASP.NET Core Identity 创建用户并授予初始系统管理权限。用户、初始授权和初始化标记一同提交。后续启动保留库中的密码和授权，停用管理员也不会触发重新创建。部署可从受保护的文件或环境注入秘密。其余用户由具有开户权限的管理员创建，MVP 不开放自助注册。开户与授予管理权限分别校验。

官方 CLI 和桌面 client 可以在主节点的 HTTPS 账户服务建立第一方会话。以 CLI 为例，用户在终端输入账户名及不回显的密码，client 验证预先选定的主节点，直接向它提交登录请求。主节点用 ASP.NET Core Identity 验证账户及密码、执行适用的登录限制，再签发可撤销的用户会话。业务从节点只接收面向该服务的凭据，账户密码只提交给主节点。首次登录无需浏览器、第二台设备或设备登记。官方 CLI 和桌面 client 属于本产品既有的信任范围。直接登录时由它们接收密码并交给主节点验证。若改用系统浏览器，则由主节点登录页接收密码，client 只取得授权结果。项目负责第一方会话的签发、到期、续期和撤销。密码哈希继续复用 Identity。ASP.NET Core 的 IdentityV3 使用 PBKDF2-HMAC-SHA512、128 位随机盐和 256 位派生值，默认迭代 100,000 次。[OpenBao 的账户密码登录](https://openbao.org/docs/auth/userpass/) · [Argo CD 的本地登录与 SSO](https://argo-cd.readthedocs.io/en/latest/user-guide/commands/argocd_login/) · [Identity 密码实现](https://github.com/dotnet/aspnetcore/blob/v10.0.15/src/Identity/Extensions.Core/src/PasswordHasher.cs)

OAuth 也适用于同一产品。浏览器授权码与 PKCE 可让密码只进入主节点的登录页，RFC 8628 可让用户在另一台终端确认。它们适用于需要统一登录页、外部身份提供方或显式委托的场合。项目自有的第一方会话是独立候选，不采用 OAuth 密码授权。IETF 的第一方应用草案引入原生授权挑战端点，将具体身份验证步骤留给部署方，尚未成为 RFC。Kerberos V5 则是成熟的集中票据认证标准，客户端能用服务票据向目标服务证明身份。完整采用它需要管理 KDC、服务主体、密钥和时钟，产品仍须定义设备审批和业务权限。[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4) · [IETF 第一方应用草案](https://datatracker.ietf.org/doc/draft-ietf-oauth-first-party-apps/) · [Kerberos V5](https://www.rfc-editor.org/rfc/rfc4120.html)

项目自有的登录、开户、设备入网及业务操作按 Proto 约定声明。选用 OAuth 的流程可由 OpenIddict 处理相应标准端点，第一方登录和设备委托均由同一账户服务确认用户及其权限。[API 开发指南](../../docs/development/api-design.zh.md)

## 从节点如何校验权限

主节点必须保持可连接，并掌握会话、设备、委托与权限的权威状态。设备审批、权限变更和新任务派发在主节点核对最新状态。长轮询在交付任务前复核，已领取任务中的本地步骤和流记录使用该次尝试的授权。业务从节点按需向主节点取得授权决定，允许的结果可以在有效期内复用。

主节点维护实例标识和全局撤权序号。凡是可能使已缓存的允许结果失效的变更，都随变更提交递增该序号，例如会话撤销、设备停用、委托范围缩小或权限关系移除。开户、签发新会话和只增加权限的变更保持原序号。授权响应包含计算该决定时的实例标识和序号，现有协调心跳响应也携带这两个值。

从节点只缓存允许结果，按凭据、账户、目标服务、资源 URI 或授权范围及读写模式划分。设备代办还绑定设备证书和委托。缓存命中时，接收端核对实例、已知最新序号、有效期及当前对象的账户归属，并检查请求实际出示的凭据。缓存缺失、版本落后或已到期时，按需向主节点重验。从节点在同一实例内只向前推进序号，收到早于已知序号的验权响应时重新查询。主节点实例变化或断线重连后清空授权缓存，随后随业务访问逐笔填充。

从主节点提交变更到从节点观察到新序号的心跳等待和并发时序计入生效延迟。各授权决定有独立有效期，受相关凭据和委托的期限约束。心跳不延长已有授权的有效期。主节点不可达且本地没有可用决定时，报告授权服务不可达。具体的有效期和连接失效判定在产品实现时确定。[RFC 7662 缓存取舍](https://www.rfc-editor.org/rfc/rfc7662.html#section-4) · [多节点协调 Note](2026-11-19-mvp-coordination.zh.md)

## 凭据保管

用户会话由 client 持有，设备私钥和设备受托凭据由该设备的 server 持有，签发私钥由主节点账户服务持有。各平台的存储后端、落盘位置与备份恢复安排留待后续决定。

## 管理员批准设备入网

1. 从节点的 server 在本机生成 ECDSA P-256 私钥，用 SHA-256 签署 PKCS#10 证书请求，通过 HTTPS 验证配置的主节点并提交请求。账户服务验证 CSR 签名与公钥，将公钥固定在该请求上。它返回私有的随机领取凭据、供人核对的显示码、验证入口和轮询间隔。服务端保存领取凭据的摘要，待批请求有期限，并按显示码的熵限制猜测。私钥始终留在设备。
2. 管理员在已登录的 client 中核对显示码和设备展示的公钥指纹。账户服务校验设备审批控制 URI 的写权限，并记录审批者与决定。批准后，签发方分配稳定设备 ID，按自己的证书模板签发仅供 TLS 客户端认证的 X.509 证书，登记证书指纹和状态。名称、用途和扩展由签发方决定。一次批准只创建一个设备身份。
3. 从节点用私有领取凭据轮询。待批时按指示退避，拒绝和过期有明确结果。服务端持久化签发结果，有效期内重领返回同一设备 ID 和证书。设备以私钥和证书通过 mTLS 证明身份。每次领任务、包括长轮询真正交付前，仍核对设备是否启用。续期时以有效设备凭据提交新 CSR，密钥丢失则重新审批。诊断与任务载荷不记录领取秘密或私钥。

建议复用 .NET 的 `CertificateRequest`、Kestrel 和 ASP.NET Core Certificate Authentication。项目维护待批请求、设备登记和幂等签发。Kubernetes 将节点申请、审批和证书签发分开，EST 定义了等待人工审批时的重试响应，两者都能直接指导本流程。管理员的批准只授予设备入网资格，用户可以在之后另行委托。[Kubernetes 节点引导](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-tls-bootstrapping/) · [EST 人工审批](https://datatracker.ietf.org/doc/html/rfc7030#section-4.2.3) · [.NET 证书认证](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/certauth)

## 用户授权设备代办

用户在主节点确认哪台设备可以代自己访问哪个账户、哪些业务能力及其读写模式。账户服务记录委托、期限和撤销状态，并给设备签发单独的用户访问令牌。用户主体保留在令牌中，RFC 8705 的 `cnf.x5t#S256` 将令牌绑定到设备证书。设备调用目标服务时出示两者。接收方校验设备当前状态、令牌受众、证书绑定和仍然有效的委托，再核对用户当前权限及资源归属。用户会话和设备证书即使各自有效，也不能替代这项委托。撤销委托只终止这项代办，设备仍可按自身资格领任务。设备停用或换证后，旧委托令牌不能配合其他证书使用。[RFC 8705 证书绑定](https://www.rfc-editor.org/rfc/rfc8705.html#section-3) · [OpenIddict 双向 TLS](https://documentation.openiddict.com/configuration/mutual-tls-authentication)

有可用回调的设备可走带用户同意的授权码流程。无界面的设备可考虑 RFC 8628，由用户在另一台终端登录并同意委托。OpenIddict 7.9 的内置 PKI 客户端认证还要求设备证书匹配该 OAuth 客户端注册的回调主机。无回调设备的候选做法，是在库提供的证书验证扩展点核对已登记的 OAuth 客户端、设备 ID、证书及有效证书链。这条路径还需单独验证。用户访问的 HTTPS 入口无需客户端证书。需要证明设备身份的调用使用独立监听地址或 TLS 主机名，同一业务操作按验证后的调用上下文授权。[RFC 8628 用户授权](https://www.rfc-editor.org/rfc/rfc8628.html) · [OpenIddict 证书验证源码](https://github.com/openiddict/openiddict-core/blob/7.9.0/src/OpenIddict.Core/Managers/OpenIddictApplicationManager.cs)

## 主节点的分层 URI 授权

### 资源与授权关系

主节点账户服务保存账户和设备的归属关系及显式 URI 授权。数据、操作入口和授权配置都使用同一种 ACL。授权针对主体、资源 URI 和读写模式。读写独立，因此任务投递口可以只写。读取、列举和搜索只展示可读资源。拒绝写入时，读取权限决定能否披露资源存在。

用户标识用于确认操作者，账户标识用于界定业务数据的归属。个人账户所有者默认可以读写本账户的业务资源，分享通过为其他主体增加显式授权实现。授权配置使用自己的 URI 和继承边界，首版由账户或设备所有者管理相应授权。系统控制 URI 分别承载开户和设备审批等权限。以后引入组授权时仍使用同一套 URI 权限。

业务插件以加载时确认的插件 ID 标识 URI 命名空间，并定义其中的资源和读写语义。账户数据采用 `lazytuihub://<plugin>/accounts/<account>/<collection>/<id>`。父级授权按完整路径段继承，账户服务只保存采用规范路径段编码的授权。账户和设备所有者在同一 URI 体系下分别通过 `core/accounts/<account>/grants` 和 `core/devices/<device>/grants` 管理分享。设备任务入口 `core/devices/<device>/jobs` 单独授权。插件处理普通引用时另行检查目标 URI。数据资源以业务身份和账户归属标识，更换承载设备后可以沿用同一 URI 与授权。[插件标识与资源命名空间](2026-11-17-mvp-plugins.zh.md)

### 设备能力与用户委托

设备登记记录所有者。所有者默认可以使用该设备，也可以把相应能力授给其他用户。用户直连使用设备提供的能力与计划器为运行主体选择这项能力时，都检查同一个资源 URI，例如设备任务入口的写权限。具体能力以设备的导出范围为准。访问设备承载的业务数据时，检查该数据的 URI，执行位置由资源绑定决定。设备自身凭入网取得的身份向协调服务上报资源、领取任务和回执。[多节点协调 Note](2026-11-19-mvp-coordination.zh.md)

设备代办按账户、业务能力和读写模式授予。在受托调用中，框架对本次操作涉及的每个 URI 取用户权限和委托范围的交集。派发后的工作还受该次尝试的目标和操作约束。设备使用权授给使用某项设备能力的主体，用户委托授给代表用户调用资源的设备。

### 共用验权与插件数据访问

框架提供单个和批量 URI 读写判定，也可查询本次调用在指定资源范围内的有效权限。所查询的范围由插件按本次业务操作选定，可以涉及多个插件的命名空间。框架统一核对凭据、计算 ACL 与委托交集、处理允许结果缓存。主节点依据明确的 URI 判定授权，将业务对象的查找和解释留在插件所在节点。

插件用可信账户和业务对象的归属解析本次操作对应的 URI，并保证实际读写落在同一授权范围内。比如，文章请求只带文章 ID 时，文章插件在可信账户和约定的业务范围内确定目标。若产品允许通过分享的订阅访问其文章，插件确认实际从属关系，并检查这次访问对应的 URI。共用的应用服务将这套规则用于 HTTP、CLI、桌面和工作流。

插件向自己的 DAO 传入可信账户 ID 和获准的目标对象或集合。单对象的查找和更新按这两个条件定位数据，列表与全文检索先应用可见范围再分页。对象 ID 和游标在相应的账户及查询范围内解析。框架返回授权决定或范围，插件决定如何应用到查询、索引和写入，DAO 提供者可为相同存储后端提供复用工具。[DAO 与业务存储边界](2026-11-17-mvp-storage-dao.zh.md)

共享 SQLite 时，订阅 URL 和幂等请求 ID 在账户内唯一。RSS 和文章插件在读写与文章全文检索中应用账户和 URI 可见范围。订阅、文章、抓取明细和数据关联都带有账户归属。当前工作流定义仍是安装级共享元数据。用户工作流和持久运行记录随协调方案推进。[订阅存储](../../plugins/LazyTuiHub.Plugin.TuiHub.Rss/Backend/RssStore.cs) · [文章存储](../../plugins/LazyTuiHub.Plugin.TuiHub.Articles/Backend/ArticleStore.cs)

## 实现范围与剩余验收

主节点支持第一方 HTTPS 登录，用 ASP.NET Core Identity 散列密码，签发随机 Bearer 会话并只保存其摘要，支持显式注销。初始化后的用户由管理员在主节点创建。CLI 可在无浏览器环境向远程主节点登录，也可为本地命令传入会话。桌面可用已有会话启动。远程与本地业务调用共用插件验权。会话默认有效八小时，覆盖一个工作日，可由配置调整。本轮 MVP 使用新的工作区结构。

协调器在生成计划和实际派发前检查当前 URI 授权，账户模式沿用对端配置凭据和推送传输。工作节点接收协调器指定的账户范围，将执行权限限定在已声明的操作资源范围内。RSS 在显式刷新时运行，等定时任务能携带可信主体后再接入自动刷新。设备入网签证、证书绑定的用户委托、从节点允许结果缓存、用户组与权限组、持久化轮询协调仍待实现。[主节点与工作节点集成测试](../../tests/LazyTuiHub.Tests/AccessTests.cs)

独立原型用 OpenIddict 7.9.0 和两个 HTTPS 监听地址验证了授权码与 PKCE、令牌撤销、同一令牌下的组权限移除、管理员审批 CSR、重复领取同一设备身份、设备 mTLS 和既有连接上的设备停用。证书绑定令牌只接受登记证书，撤销委托后设备仍可独立领任务。实验使用已登记回调和程序化用户同意。

下一轮用产品入口验收以下行为。

- 同一用户从进程内和远程操作得到相同结果。从未登记为设备的安装，用户登录 client 后即可直连远程业务 server。已登记的安装也可单独使用用户会话。双身份调用可追溯到用户、设备和委托，单独的设备身份无法读取用户文章。
- 首位管理员配置只在初始化时生效。其余用户由管理员创建。普通用户无法审批设备，拒绝、过期、重复领取和撤销都有可区分的结果。移除用户权限后，在线授权与新派发立即采用新权限。从节点在同一有效授权范围内连续翻页时，主节点的验权次数不随页数增长。仅增权时已有允许结果可以继续使用。收到撤权序号后，旧决定和迟到的旧版验权响应均不得放行新的请求。重连和主节点实例切换后验证缓存按需重建。
- 用独立的主节点和业务 server 验证第一方 CLI 首次密码登录、直接访问业务节点、主节点失联和恢复、设备换证。采用 OAuth 时再验收对应的回调或异机确认，另验无界面设备的委托流程。
- 两个账户可在同一 SQLite 中使用相同 URL 和幂等键。成员访问文章时，验权和实际查询使用同一账户与对象范围，标记已读、搜索、分页和执行尝试标识也适用这条边界。个人账户所有者按默认授权访问业务数据，系统管理员按相应资源的授权访问他人数据。
- 设备使用权可以单独授予和撤销。只有设备使用权的用户可以提交获准的任务，但访问他人数据或修改设备授权仍须通过对应 URI 的检查。只写任务入口允许投递，读取仍按其自身授权判定。
