# 全仓防御程度与工程取舍

[English](2026-11-16-defensive-posture.en.md) | 中文

## 范围与目的

本 Note 为整个仓库建立统一的防御取舍原则，覆盖产品代码、协议、持久数据、内部调用、测试、依赖、开发工具、CI、部署、文档和 Agent 工作流。防御包括输入校验、错误处理、限制、兼容分支、权限隔离、版本固定和自动化门禁，不只指安全扫描。

本 Note 记录已采用并用于当前仓库审查的防御程度约定。implemented 表示原则已生效及本次必要调整已落实，不表示所有未来业务机制已经实现，也不将本次核对作为完整安全审计的结论。

## 覆盖式维护

本 Note 生效后正文冻结。需要变更正文或约定时，新建一份完整的双语 Note，写明继续有效的全部原则及新选择，不用增量补丁分散维护本主题。新 Note 先为 proposed，经语义覆盖核对并落实后转为 implemented；草案未生效前，当前 Note 继续有效。

新 Note 完整覆盖旧 Note 后，将旧 Note 转为 archived，仅修改 status 和 superseded_by 元数据以引用新 Note，保留旧正文和其他元数据。此主题使用完整替代，不以长期并存的部分 superseded 记录维护原则。同步更新项目 Skill、AGENTS.md 及其他当前入口，使其指向新的有效 Note。

复用既有 Note 元数据及生命周期检查。完整语义覆盖仍由维护者审阅，不新增维护字段、旁路记录或仅为这份原则建立专用校验器。

## 默认立场

默认采用满足实际需求和明确约定的最小防御。根据输入来源、信任边界、失败后果和维护成本作判断，不把保守程度、检查数量或失败得更早本身当作质量目标。

以已知约束、实际故障、可信的风险分析和当前操作的后果作为依据。增加一项措施，应能说明它保护什么、通过什么机制起作用，以及为何值得承担实现、运行和维护成本。通用最佳实践和工具建议是参考，不能直接替代项目判断。

信任按数据来源和语义边界划分。进程内调用不自动拥有业务权限，本地文件也可能来自外部；受控内部代码可以依赖已经建立的类型和不变量。身份、授权或持久数据安全所需的前提无法成立时，明确失败，不将不确定性解释为允许执行。

## 各部分的防御边界

| 部分 | 默认程度与责任 |
| - | - |
| 公网 API、WebSocket 及其他外部输入 | 按不可信输入处理，在相应边界校验协议结构、调用身份、权限和业务约束。必要的资源保护依据实际成本与风险确定；不自行增加字符集、长度或功能白名单。 |
| 进程内 API 与应用服务 | 共享业务校验、权限语义及写入约束。直接调用应用服务，避免回环 HTTP、重复序列化或模拟传输上下文来获得形式上的一致性。 |
| 领域逻辑与状态变更 | 维护真实业务不变量、事务和副作用的一致性。去重、并发控制和操作恢复在相应业务出现时落实，不为无状态样例预建通用系统。 |
| 内部模块、依赖注入与类型边界 | 优先使用类型、构造过程、nullable 和明确的调用约定。已在责任边界保证的条件不逐层重复检查；编程错误清晰暴露，不通过空结果、默认成功或大范围捕获掩盖。 |
| 存储、文件与外部服务调用 | 正常处理实际可能发生的 I/O 和通信失败，遵守数据所有权、事务及约定的覆盖和恢复语义。写入结果未知时保留该语义；重试必须符合操作的幂等性，不能把重试当作通用修复。 |
| 产品 lint、测试与生成代码 | 执行已约定的产品规则，测试直接表达场景，生成源码通过编译与一致性检查。不为通过 lint 拆散测试、增加无意义逻辑或手工整理生成器风格；新增测试服务于具体风险。 |
| SDK、依赖与 GitHub Actions | 区分构建兼容、来源信任和执行权限，使用生态已有机制。版本固定或跟随更新分别衡量，不因存在供应链风险就默认对全部依赖采取最重固定策略。 |
| 本地 CLI、初始化与开发辅助 | 校验执行确实需要的参数、路径、所有权和可用条件，错误可诊断。保留已有配置及用户修改，不为未承诺的历史用法建立额外拒绝、迁移或兼容框架。 |
| CI 与自动化检查 | 为 main 的可取得快照和真实执行结果负责，使用所需最小权限。验证承诺的平台和能力，不审计开发者本地过程，不要求无法取得的信息；工具执行失败仍如实报告。 |
| 部署、发布与凭证 | 按实际操作授予权限并保护凭证和持久数据。涉及真实外部副作用时落实相应隔离与恢复措施；额外签名、审批或审计系统需有具体需求。 |
| 文档、Notes、Skill 与 Agent | 保留当前约定、决策依据和必要证据，按任务读取相关资料。遵守明确的 Note 生命周期和生成边界；不因无法自动证明语义正确就增加旁路凭据、重复记录或新的形式门禁。 |

## 限制、错误与兼容

资源预算和功能限制分别判断。CPU、内存、并发、重试预算等可以依据资源成本及运行目标设置；输出长度、文本字数、数据大小或允许类型等功能边界，需要实际需求、明确依据或用户约定。必要性或具体阈值尚不明确时，先说明影响和取舍，不自行选择一个保守值。

采用上游默认值前核对其行为，特别是内容丢失、静默截断、自动重试和错误处理。默认值也有后果，不能以“上游默认”代替适用性判断。现有仓库文件上限为 1 MiB（1,048,576 字节），继续约束已跟踪文件及未被忽略的新文件，不将它推广为业务文件或 API 请求上限。

对可安全处理的未约定行为，不主动新增拒绝分支。兼容性依照已经承诺的使用方式设计，不自动承诺所有旧版本、历史调用和平台。错误在相应责任边界处理，不静默吞掉、截断数据或伪装为成功，也不因假想故障无限叠加 fallback。

## 依赖与版本引用

已有 SDK、编译器和协议工具版本继续作为构建基线，以各自权威配置为准；包与锁文件继续使用当前生态机制。不能因为本 Note 强调维护成本，就擅自放宽现有明确的版本约定，也不在另一处重复维护同一版本。

可信官方或维护者提供的 Action 可以使用其受支持的主版本标签，接受相应维护更新。需要固定某次实现、存在具体审计要求，或执行权限及后果值得更严格控制时，可以固定完整 SHA，并同时考虑更新方式与长期成本。第三方来源本身也不自动意味着必须锁 SHA；来源、权限、用途和维护能力共同决定选择。

固定引用只覆盖它实际固定的部分，不据此宣称整个运行环境可复现或安全。标签跟随更新和 commit 固定都是取舍，不能仅用“更安全”作结论，也不把某一处采用的引用方式自动推广为全仓所有依赖的默认策略。

## 增加措施的依据

提出新的校验、限制、依赖锁定、测试、兼容分支或门禁时，交代以下信息即可，放在适合的代码结构、说明或评审上下文中，不要求另建逐项登记系统：

- 要保护的具体边界、数据或行为，以及有依据的失败后果。
- 措施如何发挥作用，现有类型、框架或责任边界是否已经覆盖。
- 对正常使用、误报、维护、更新和执行成本的影响。

常规取舍根据现有约定和证据直接处理。只有确实需要用户决定、且现有上下文无法推导的行为或成本取舍，才进行澄清；假想风险不自动触发审批流程。不为满足工具而改变正确业务，也不通过降低已有门禁掩盖缺陷。
