# MVP 游戏库与元数据来源

[English](2026-11-23-mvp-games.en.md) | 中文

## 个人游戏与识别依据

Games 插件给每个账户的个人游戏分配稳定 ID。用户维护标题、分类和各设备的游玩时段。每个在线账户和每个扫描目录独立报告游戏状态。Steam 拥有记录、Bangumi 收藏状态、VNDB 标签和本机安装路径可以指向同一个游戏，各自保留来源。这里沿用 Gebura 对个人游戏和商店条目的区分，也沿用 waiter 按设备记录安装的做法。[librarian 游戏模型](https://github.com/tuihub/librarian/blob/1fcb0f342a9d35134139707446e426dd2972bb03/internal/model/modelgebura/modelgebura.go) · [waiter 游戏仓库](https://github.com/tuihub/waiter/blob/ae1ae6f349eef99a8a300ed9276c319683ef5797/lib/repo/gebura_repo.dart)

安装或收藏再次出现时，沿用已有归属。新记录可以通过相同平台 ID 或唯一的跨站映射归入已有游戏。匹配时双向检查映射行数及各站点的 ID 数量。多个候选指向不同游戏时单列新条目，留给用户确认。标题用于搜索。用户可以重新分配安装和收藏、给个人游戏关联多个来源，也可以让同一商店合集描述多个游戏。[TuiHub ID 数据集](https://datasets.tuihub.org/game_id_list.json)

## 公共目录与个人元数据

Games 通过 `IGameCatalog` 注册搜索和查询操作。Steam 为自己的目录实现取得 HTTP 客户端，Bangumi 和 VNDB 注册 SQLite 目录。provider 命令与游戏库的整理操作调用同一组类型化工作流。导入要求工作流返回一个且仅一个 `GameEntry`，缺少该结果时两个入口都报告失败。

Bangumi 和 VNDB 以只读模式打开各自上游的 SQLite 目录。三个字符及以上的检索使用三元组标题索引，较短的检索使用子串匹配。Bangumi 只选游戏条目。VNDB 读取原语言标题、译名、发行日期、封面 ID 和制作发行方。[Bangumi SQLite PR](https://github.com/tuihub/bangumi-db/pull/1) · [VNDB SQLite PR](https://github.com/tuihub/vndb-db/pull/1)

Steam 按配置的地区和语言搜索商店，保留商品类型。联网查询前，Steam 插件按商店的 robots.txt 检查 LazyTuiHub 能否访问目标路径，并遵守上游限流。本地 JSONL 也可以提供 Steam 商店样本。[Steam 商店 robots.txt](https://store.steampowered.com/robots.txt)

各账户共享可替换的公共目录。用户确认关联后，provider 工作流将条目快照写入主工作区，快照和框架关系在同一事务中提交。停用插件或移走目录后，Games 仍可显示已入库的资料。详情页逐字段显示来源，优先采用用户覆盖值，再从按来源名及原始 ID 排序的快照中取首个有值的字段。刷新保留个人编辑，解除关联时一并删除对应关系。用户可以依据已安装目录和无歧义 ID 一次补全多个来源，也可以逐站搜索、人工确认。

## 账户绑定与同步

第三方账户归属于当前 LazyTuiHub 账户。绑定按平台的稳定账户 ID 区分，同一平台可以连接多个账户。绑定和同步检查本账户的 connections URI，改动游戏库时另行检查游戏库 URI。公共资料工作流传递来源 ID，本地账户适配器持有第三方凭据。主机通过 ASP.NET Core Data Protection 按账户、平台和平台用户 ID 保护令牌。现有密钥环位于工作区数据库同目录的 `keys/` 中，需与工作区一并保护和备份。[账户与资源访问](2026-11-19-mvp-account-identity.zh.md)

| 平台 | 如何证明账户归属 | 只读同步 |
| - | - | - |
| Steam | 系统浏览器通过 Steam OpenID 2.0 登录，临时回环地址接收断言，主机直接向 Steam 验证。 | 主机使用 Web API Key 调用 GetOwnedGames。若 Steam 未向该 Key 披露游戏详情，保留上次快照。 |
| Bangumi | 个人访问令牌通过 `/v0/me` 验证并取得平台用户 ID。 | 每次同步先核对数字 ID，再用最新用户名分页读取收藏，保留每款游戏的收藏状态。设置用户名后，此接口要求使用用户名。 |
| VNDB | 个人令牌通过 `/authinfo` 验证，绑定时检查 `listread`。 | 同步前再次核对账户和权限，再用作品 ID 逐页读取列表和标签，直至末页。 |

适配器先取完数据，再用一个 SQLite 事务更新该来源的全部记录。取消、分页中断或绑定在同步期间发生变化，都会保留原快照。只有成功取完数据，才能把本次缺失的记录标为已移除。个人游戏、安装、资料快照和编辑记录继续保留。断开账户会清除凭据，并在上次成功同步的记录上显示已断开。停用 provider 后仍可浏览已入库的数据。[Steam 身份验证](https://partner.steamgames.com/doc/features/auth) · [Bangumi API](https://github.com/bangumi/api) · [VNDB Kana](https://api.vndb.org/kana)

## 游戏库的浏览与维护

Games 默认展示整页封面墙，也可切换成紧凑列表。卡片保留标题，封面缺失或加载失败时仍占据同样的版面。按标题和别名搜索，按安装、在线收藏、待识别、分类或资料来源筛选。选择游戏后，宽屏在书架旁展开详情，窄屏单独展示详情。返回时保留筛选条件，将焦点送回仍在结果中的游戏。概览卡片整体响应点击、悬停和键盘焦点，编辑表单预填当前资料，目录选择器与路径输入并排。这些细节参考了 waiter 已验收的游戏概览与资料编辑。此处的层次服务于跨来源的个人收藏，标题和主要操作也可直接触控。[waiter 游戏概览](https://github.com/tuihub/waiter/blob/ae1ae6f349eef99a8a300ed9276c319683ef5797/lib/view/pages/gebura/gebura_library_overview.dart) · [waiter 编辑表单](https://github.com/tuihub/waiter/blob/ae1ae6f349eef99a8a300ed9276c319683ef5797/lib/view/pages/gebura/gebura_library_detail_app_panel.dart)

打开详情时，页头和工具栏保持原位。宽屏在工具栏下分栏，窄屏切换整页，返回时恢复原游戏、键盘焦点和滚动位置。分类与资料来源在按钮下方的浮层中选择。四档筛选为选中状态预留宽度，底部状态提示浮在网格之上。

三套设计分别为标题、正文和辅助文字指定字号与行高。封面保持 2:3，网格为两行标题和一行副标题预留空间。Fluent 与 Material 按行对齐副标题。Mac 外观参照原生样板，让副标题紧随标题末行，单行标题下的副标题比双行标题高 16 点。列密度、间距和详情宽度由本项目选定。键盘焦点用单层轮廓标示，可与当前游戏的选中底色同时显示。Material 使用色调表面与筛选标签，macOS 使用分段控件，Fluent 使用强调色下划线。面板随渲染帧淡入并短距平移，Fluent 用 167 毫秒，macOS 用 200 毫秒，Material 用 250 毫秒。应用内可减少动态效果，也会遵循 macOS 和 Windows 的系统减弱动效设置。[Microsoft 字阶](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography) · [Microsoft 布局间距](https://learn.microsoft.com/en-us/windows/apps/design/layout/alignment-margin-padding) · [Microsoft 动效](https://learn.microsoft.com/en-us/windows/apps/design/motion/timing-and-easing) · [Apple 字阶](https://developer.apple.com/design/human-interface-guidelines/typography) · [Apple 集合布局](https://developer.apple.com/design/human-interface-guidelines/collections) · [Apple 动效](https://developer.apple.com/design/human-interface-guidelines/motion) · [Material 自适应布局](https://developer.android.com/codelabs/adaptive-material-guidance) · [Material 字阶](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-typescale.scss) · [Material 动效](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-motion.scss)

11 月 25 日，Argon 查看三套主题的实际界面、键盘焦点、动画中间帧和 macOS Retina 渲染后，通过了本轮游戏库视觉验收。在 390 个逻辑单位宽的窗口内，Fluent、macOS 和 Material 的首排两张封面分别从纵向 165、157 和 185 处开始。打开筛选浮层时书架位移为零，打开详情时页头操作保持原位。当时 13 款样本游戏的副标题均与同行对齐。原生渲染验证在 macOS 上完成。后续人工验收发现两处 Fluent 回归。卡片现由专用按钮主题控制，外框统一绘制悬停、选中和键盘焦点。此前悬停着色的两层边界每边相差 7 px，修复后在 macOS Skia 的 1× 渲染中均为 158 × 296 px。图文按钮使用 20 个逻辑单位的 Fluent 行高，文字行与加号居中排列。文字的可见中心由原先高于加号 2.5–3 DIP 变为持平至低 0.5 DIP。同机微软 Fluent Web 样板在浅色下低 1–1.5 DIP，在深色下低 0.5–1 DIP。常规产品测试覆盖这两处回归，[桌面 UI 自查标准](../../docs/development/desktop-ui-review.zh.md)给出复现方式。

详情先展示作品本身，再按设备安装和在线账户列出使用情况。资料来源与游玩记录可展开查阅。**Identify** 用于搜索、确认、刷新或解除来源。**Edit info** 在一次提交中保存标题、分类和修改过的字段，也可恢复来源值。**Reassign** 针对一条安装或收藏记录，可移到另一款游戏，或新建条目接收该记录。

**Sources** 将平台账户和本地目录分开。各平台集中展示自己的账户、同步状态及可用操作。Steam 扫描器跟随 libraryfolders.vdf 并读取安装清单，普通目录扫描器枚举根目录的直接子目录。设备与路径共同标识安装位置。主机 CLI 提供相应的管理操作。远程管理 API、启动游戏及自动记录游玩时长留待后续讨论。

将 `Games__bangumi__Database` 和 `Games__vndb__Database` 指向解压后的 SQLite 文件，也可以放到本地应用数据目录下默认的 `LazyTuiHub/catalogs/{provider}.sqlite`。将 `Games__IdDataset` 指向下载的 game_id_list.json。同步 Steam 库还需设置 `Games__steam__WebApiKey`。两个上游 PR 附有本机构建步骤，合并后维护者可以手动发布压缩目录和校验和。

```sh
mise run run:desktop
mise run run -- --command games --action scan --scanner steam --root /path/to/SteamLibrary
mise run run -- --command games --action shelf
mise run run -- --command games --action fill --game GAME_ID
mise run run -- --command games --action show --game GAME_ID
```

本轮使用包含 119,444 个 Bangumi 游戏和 68,340 部 VNDB 作品的真实转储验证。跨站数据集将 Steam 324160、Bangumi 13 和 VNDB v4 对应到 CLANNAD。扫描安装清单并补全资料后，同一条目显示 Bangumi 的发行日期、VNDB 的封面和开发商。账户同步用协议样本覆盖 Steam OpenID 验签、分页中断和隐私受限等情形。[游戏库存集成测试](../../tests/LazyTuiHub.Tests/GameInventoryTests.cs)
