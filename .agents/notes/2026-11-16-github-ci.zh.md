# GitHub CI 检查

[English](2026-11-16-github-ci.en.md) | 中文

## 状态与范围

本 Note 规划 GitHub Actions 对 main 分支当前提交快照的质量检查，复用已落地的[仓库初始化基线](2026-11-15-repository-initialization.zh.md)、[C# lint](2026-11-15-csharp-lint.zh.md)及[协议与生成基线](2026-11-15-protobuf-api-contract.zh.md)。范围仅为 CI，依赖更新、发布、网页部署、协作模板和仓库规则配置另行讨论。

已编写 CI 和 CodeQL workflow，并提供可本地执行的检查入口。本地验证不代表 GitHub Actions 已运行。本 Note 保持 proposed，等待真实 main 事件与 runner 验收。

CI 为主分支的交付状态负责。开发者的本地检查、开发分支、PR 提交整理和 Agent 决策过程继续遵循各自约定，不成为这份 CI 的验证对象。

## 触发与检查对象

CI 和 CodeQL 均仅在 main 的 push 事件运行，检出该事件指向的确定提交；运行期间 main 再次更新，也不切换正在检查的提交。事件含义以 [GitHub 官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)为依据。

检查目标是该提交中的代码、声明、配置、派生产物和文档是否自洽、可构建且满足现有质量约定。报告实际提交、平台和检查结果，不追溯整个开发流程。

CI 不校验 PR 标题、开发分支的全部提交消息或本地 hook 是否运行，也不运行 Note 跨提交生命周期门禁。Note 当前元数据、引用和文档结构仍通过 Markdown 管线检查。主分支的 Conventional Commits 约定和 Note 生命周期继续由本地工具及审阅执行。

## 复用任务与平台

通过 [mise.toml](../../mise.toml) 的共享任务执行检查，不在 workflow 重写规则。`check:ci` 聚合当前快照检查、workflow 校验、工具测试和 API 调用验证，不包含本地提交消息或 Note 历史门禁；本地 `mise run check` 继续保留自己的完整默认行为。

| 检查组 | 平台 | 执行内容 |
| - | - | - |
| quality | Linux | 执行 check:ci：文件、Markdown、C#、API、actionlint、产品测试及现有辅助工具测试；demo:api 已包含 check:api。 |
| platform | macOS、Windows matrix | build 和 demo:api，核对同一提交在另外两个现代系统上的构建及调用链路。 |
| CodeQL analyze | Linux，按语言分为 JavaScript/TypeScript 和 Actions 两项 | 官方默认查询扫描辅助脚本与 workflow，上传 Code Scanning 结果。 |
| 结果展示 | GitHub 原生运行结果 | 不额外创建汇总 job；各 job 和 matrix 项直接保留其成功、失败或取消状态。 |

`test:tools` 使用 Node 内置 runner 执行现有 `.agents/tests/*.test.mjs`，其中已包括 test:lint 对应的测试文件，不重复运行同一组。测试验证辅助工具本身，不审计此次开发过程。test 任务执行 xUnit 产品测试程序，用临时工作区与本地 fixture 验证管线、RSS、SQLite 及本地/HTTP 行为，继续保留产品测试与产品分析器的既有隔离。

首版以 main 当前快照的完整检查为基线，平台无关的检查集中 Linux，其他平台只执行有平台价值的构建和调用验证。暂不建设受影响依赖图，不要求每次本地编辑或开发分支推送运行上述矩阵，也不设置每日全量策略。

## 工具与执行环境

使用维护者提供的 [mise-action](https://github.com/jdx/mise-action)准备 GitHub 托管 runner。SDK、Node.js、pnpm、C# 和协议工具读取现有权威声明，不在 workflow 复制版本。新增 actionlint 的固定版本也由 mise 管理，check:workflows 检查 Actions 语法、表达式和 job 配置。按[全仓防御约定](2026-11-16-defensive-posture.zh.md)核对来源、权限和维护成本后，checkout、CodeQL 及 mise-action 使用各自维护者提供的主版本标签；不增加缺少具体依据的统一 SHA 固定策略。

显式安装所需工具、按 frozen-lockfile 安装依赖、还原本地 .NET 工具，并执行 setup:aip 准备固定提交的官方原文。Doctor 保持只读诊断。源码与派生产物由检查读取，CI 不修复、重新提交或放宽 1 MiB 文件上限。

普通 CI 使用 contents:read，checkout 不保留写入凭证，不依赖仓库 secrets 或特权事件。CodeQL 单独使用上传安全结果所需的 security-events:write，以及官方模板为私有仓库读取运行信息所需的 actions:read；这些权限不赋予普通 CI。事件值通过数据或安全参数传入，不直接拼进 shell 源码。依据见 [GitHub 安全说明](https://docs.github.com/en/actions/reference/security/secure-use)。

## CodeQL 覆盖与兼容性

采用 GitHub 官方 [CodeQL Action](https://github.com/github/codeql-action)，扫描配置在 [.github/codeql/config.yml](../../.github/codeql/config.yml)。当前扫描 `.agents/scripts/` 和 `.github/workflows/`，保留官方默认查询，不扩大为额外质量规则集。分析完成后上传结果；workflow 成功表示分析及上传完成，不等于没有安全警报。

核对时[官方支持表](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)列出的 C# 上限为 C# 14、.NET 10，低于本仓 C# 15、.NET 11。当前不启用 C# CodeQL，也不为接入扫描降低项目工具链或引入实验性扫描。C# 继续执行已有分析器与构建检查；这不等同于已有 C# CodeQL 覆盖。待官方支持当前工具链后，再增加相应扫描及实际构建提取验证。

GitHub Code Scanning 需要目标仓库具备该功能的使用资格及相应权限，具体以[官方说明](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning)为准。当前没有远程仓库上下文，不宣称已验证账号功能、SARIF 上传或远程扫描结果。

## 信息边界与执行成本

CI 只依据检出树、运行结果和实际可读取的事件信息。它无法知道开发者未提交的工作区、提交前的中间状态、从未入库的 proposed 状态，也不能证明语义审阅已经发生；不为这些信息设置门禁或维护过程 sidecar。

当前快照检查不依赖完整 Git 历史、push 前的提交或 PR 历史。首次推送、历史重写或读取权限受限，不应仅因缺少这些信息而失败。需要执行的检查本身发生工具、依赖或命令错误时，仍按实际失败报告。

取消被新 main 提交替代的运行以节省资源，新的运行仍检查完整快照，避免前一轮被取消后遗漏验证。缓存只加速工具与依赖获取，按平台和权威配置区分；缓存命中后仍执行检查，不缓存成功结论或用旧生成结果代替比较。

先观察冷启动和缓存后的耗时，再优化缓存、任务分组及执行预算。以后若引入按变更选择，应以已验证的主分支基线为依据；无法确定影响时完整检查当前快照。本 Note 不新增产品测试运行时间或覆盖率门槛。

## 实施与验收

已增加 [.github/workflows/ci.yml](../../.github/workflows/ci.yml) 和 [.github/workflows/codeql.yml](../../.github/workflows/codeql.yml)。普通检查与 CodeQL 因权限和执行方式不同而分开；quality 内共用环境准备，平台检查使用 matrix，不引入额外复用 workflow 或汇总 runner。共享入口保留在 mise，不新增开发过程校验器或改变本地任务默认语义。

本地验收运行 check:ci、check:notes 和 check:commit，分别验证快照任务与保留的本地约定。确认目标 GitHub 仓库与 Actions 可用后，再在 main 的真实 push 上核实 Linux 检查、两个平台构建与调用，以及 CodeQL 语言覆盖和结果上传。已有反例测试继续确认编译、生成和文件限制等门禁，不把本地通过冒充远程 runner 验收。

本地通过、workflow 语法可解析或配置文件已提交，不足以宣称远程 CI 已生效。真实 main 事件和平台结果可核实后，再将本 Note 转为 implemented。此范围报告主分支质量状态；合并前保护或远程仓库规则不在本次配置范围。
